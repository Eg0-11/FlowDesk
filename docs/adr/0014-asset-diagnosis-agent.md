# ADR 0014：资产诊断 Agent 的确定性双 MCP 查询编排

- 状态：已接受
- 日期：2026-09-22
- 决策范围：主服务 Agent 层如何把 FD-0016 交付的两个查询端口（资产、监控）组织成一次
  「资产诊断」用例：编排归属、模型调用策略、A1/M1 证据与引用协议、三条结果路径，
  以及本阶段与 Agent Graph 的边界

## 背景

FD-0016 已经让主服务能用真实 MCP 协议读到两个独立服务的数据，但**没有人消费这两个端口**：
应用层只有查询能力，Agent 层没有任何用例。本阶段补上第一个消费者 —— 资产诊断：

```
（下一阶段的 HTTP 层）
  → AssetDiagnosisUseCase
  → 资产查询端口（asset_get）
  → 监控快照查询端口（monitoring_snapshot_get）
  → 把可用证据结构化后交给 DeepSeek
  → 校验模型引用
  → 可审计的诊断结果
```

本阶段**不**实现 Controller、**不**接入 Agent Framework / Graph、**不**把两个 MCP 查询包装成
`@Tool`/`ToolCallback`，也不改动 FD-0016 的 MCP 客户端与两个 MCP 服务。

## 决策

1. **确定性编排，而不是让模型自由选工具**：两次查询由 {@code AssetDiagnosisService} 固定执行，
   模型只负责在给定证据上写诊断。
2. **两个查询端口各调用一次，顺序固定为资产 → 监控**，第一次失败或未命中也要执行第二次；
   不重试、不并行、不缓存。
3. **模型请求里没有工具**：不注册任何 `ToolCallback`/`@Tool`，也不把远端能力暴露给模型。
4. **三条路径**：至少一侧命中 → 调用模型一次；两侧都 `NOT_FOUND` → 固定回答；
   无命中且至少一侧失败 → 固定降级回答。
5. **证据编号 A1（资产）/ M1（监控）**，模型必须用 `[A1]`/`[M1]` 引用，
   输出侧独立校验并逐条回溯。
6. **结果对象同时保留两个查询的真实状态**（含 `FAILED` + `QueryFailure`），
   不允许把部分证据包装成完整数据。

## 理由

### 为什么是确定性编排

给模型工具、让它自己决定「先查资产还是先查监控」「要不要跳过监控」，会带来三个问题：

1. **可审计性变差**：一次诊断到底查了什么、查到了什么，取决于模型这一次的决定，
   而同样的输入下次可能不同；
2. **失败被当成没数据**：模型很容易把「查询失败」理解成「这个资产没有监控」，
   而这正是本仓库一路在防的错误结论（FD-0015-R1 已经为「来源缺失」立过同样的规矩）；
3. **不可测**：无法用「端口各调用一次、顺序固定、模型调用零次/一次」这样的固定断言来验证。

因此编排权留在代码里：模型不能选工具名、不能改 assetId、不能跳过查询。
**代价**是本阶段的诊断能力是固定的两路查询 —— 要提高覆盖面就要显式改代码，
而不是让模型临场发挥；这是有意选择。

### 两个 MCP 查询端口如何进入 Agent

Agent 只依赖 application 层的两个输出端口（`AssetQueryPort`、`MonitoringSnapshotQueryPort`），
**不**依赖 MCP SDK、传输实现或两个 MCP 服务模块。因此：

- 端口实现（FD-0016 的 Streamable HTTP 适配器）可以被替换而不改动 Agent；
- 单元测试用手写替身就能覆盖全部编排规则，不需要起任何服务；
- 「远端不可用」在 Agent 看来只是 `FAILED` + 稳定分类，而不是某种协议细节。

两个端口在装配层各注入一次（`FlowDeskAiConfiguration`，只在 `flowdesk.ai.enabled=true` 时存在）。

### 三条路径

| 情形 | 是否调用模型 | 结果 |
| --- | --- | --- |
| 至少一侧命中 | **调用一次** | `grounded=true`，答案带引用，结果里保留两侧真实状态 |
| 两侧都 `NOT_FOUND` | 不调用 | `grounded=false`，固定回答「未查询到该资产或可用的监控快照。」 |
| 无命中且至少一侧失败（`FAILED`/`DISABLED`/`TIMEOUT`…） | 不调用 | `grounded=false`，固定降级回答「当前无法获得足够的资产与监控证据，暂时不能生成诊断结论。」 |

**部分命中**（一侧命中、另一侧未命中或失败）走第一条路径：允许基于**可用证据**作答，
但提示词里的 `availability` 会如实写出两侧状态，结果对象里也保留另一侧的原始三态与失败分类。
模型只知道「另一侧没有证据」，不知道也不该知道失败细节（只给稳定枚举）。

**为什么两种「没有证据」要分开**：它们对调用方的含义不同 ——
「都没查到」是一个可以接受的事实（这个资产就是没有记录/没有快照），
而「有查询失败」意味着这次诊断<b>不完整</b>，调用方可能需要重试或升级，
所以文案必须能区分，而不是都回一句「没有数据」。

### A1/M1 引用协议：保证什么、不保证什么

- 固定编号：**A1 = 资产记录**，**M1 = 监控快照**；编号不随查询结果增减。
- 模型答案里的引用被独立校验（`AssetDiagnosisCitationValidator`）：空答案、无引用、
  畸形引用（`[a1]`、`[A01]`、`[A 1]`、`[A1x]`、`[A2]`、`[A1` 未闭合等）、
  引用本次并不存在的证据、以及「本次命中的证据没有被全部引用」，一律判失败（502），
  **不修正、不补引用、不重新调用模型**。
- 只处理 ASCII 方括号；不做 Markdown/HTML 实体解码，也不做 Unicode 同形字符归一
  （全角 `［A1］`、西里尔 `А` 都不算引用意图）。

**必须说清楚的限制**：引用校验只证明<b>编号来源</b>（每个引用都能回到本次给出的证据），
它<b>不证明</b>模型结论在事实上正确 —— 模型仍然可能「引用了正确的证据却推理错误」。
本阶段没有任何环节能证明诊断结论的医学式/工程式正确性，也没有人工复核环节。

### 为什么这一阶段还不是 Agent Graph

Agent Graph 关注的是「多节点、可分支、可循环、可并行」的编排。本阶段只有一条**线性、无分支**
的路径（两次查询 → 一次生成 → 一次校验），用 Graph 框架表达只会增加一层间接：
状态机、节点注册与检查点对两个固定查询没有信息增益，却会让「各调用一次、顺序固定」
这条最重要的契约更难断言。等出现<b>真正的分支需求</b>（例如按资产类型选择不同的检查项、
需要多轮补充查询、或多 Agent 协作）时再引入 Graph，届时端口契约与引用协议可以原样复用。

### 为什么失败不等于未找到

这是本仓库反复出现的同一条原则：

- FD-0015-R1：监控服务的 `origin()` 返回 `null` 时不得写成 `source:null` 的「未找到」；
- FD-0016：断连、协议错误、非法响应都不得转成 `NOT_FOUND`；
- 本阶段：`FAILED`/`DISABLED` 不得被改写成「没有数据」，也不得被模型理解成「资产健康」。

因此诊断结果里两个查询的 `QueryOutcome` 与 `QueryFailure` 都如实保留，
提示词里的 `availability` 也只放 outcome 与稳定枚举 —— 失败是一等公民，不是噪音。

## 影响

正面：主服务第一次把两个 MCP 查询用起来；编排、模型调用次数、提示词结构与引用协议
全部可断言；失败与未找到在结果与提示词里都保持区分；Agent 不依赖 MCP SDK。
代价：诊断逻辑固定（改路径要改代码）；提示词里的证据没有历史区间、只有一条快照；
引用校验不等于事实校验。

## 已知边界与未验证项

1. **没有 HTTP 层**：本阶段只交付用例与装配，没有 Controller、没有新端点；
2. **没有真实 DeepSeek**：自动化测试用本地合成的 OpenAI 端点，
   `LIVE_SMOKE=NOT_RUN`（未对真实模型发起过任何请求）；
3. **没有真实企业数据源**：两个查询端口在测试里是替身，端到端只到「MCP 演示服务」为止，
   `MCP_LIVE=NOT_RUN`；
4. **引用校验不等于事实正确**（见上）；
5. **没有会话记忆、没有流式输出、没有工具、没有并行/重试/缓存**；
6. **单条快照**：诊断只看最近一条监控快照，没有时间序列与趋势；
7. `POSTGRES_LIVE`、`DASHSCOPE_LIVE` 与本任务无关但全仓仍为 `NOT_RUN`。

## 重新评估条件

1. 出现真实的「按资产类型分支/多轮补充查询」需求时，引入 Agent Graph 并复用本阶段端口契约；
2. 需要把远端能力交给模型时，先设计权限与审计，再显式注册工具（不能顺手把 MCP 客户端塞进模型）；
3. 需要结论级正确性时，引入人工复核或断言式校验，而不是继续加强引用校验。
