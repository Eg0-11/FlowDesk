# ADR 0004：工单列表、分页、排序与条件搜索

- 状态：已接受
- 日期：2026-09-13
- 决策范围：工单集合资源的查询接口（分页模型、排序白名单、条件组合、关键字搜索、索引策略）

## 背景

FD-0006 只暴露了单条资源的读取与一组状态变更端点，集合资源完全不可查询。
真实使用中「打开工单列表」「看我提交的工单」「搜一下标题里含某个词的工单」是最基本的诉求，
没有它们，前面的状态机与并发协议在业务上无处落地。

需要回答五个问题：

1. 分页用 offset 还是 cursor？
2. 排序字段与方向如何暴露，怎样保证不被拼进 SQL？
3. 排序的「业务顺序」与数据库的字典序不一致怎么办？
4. 关键字包含搜索怎么做，通配符与安全性怎么处理？
5. 需要哪些索引，哪些候选索引应当明确不加？

## 决策

1. **采用 `page`/`size` 的 offset 分页**，`page` 从 0 开始（默认 0），`size` 取值 1～100（默认 20）；
2. **排序字段与方向是白名单枚举**：`createdAt`、`updatedAt`、`priority`、`status` 与 `asc`、`desc`，
   默认 `updatedAt` + `desc`。客户端文本先解析成枚举常量，再由 `switch` 映射成固定的列名与关键字，
   **绝不把客户端原文拼进 SQL**；
3. **所有排序都追加 `id ASC` 作为最终兜底键**，使顺序成为全序；
4. `priority`、`status` 的排序用 `CASE` 表达式映射成业务序号，
   **不依赖数据库的字典序**，也不改动 V1 已定的表结构；
5. 关键字使用**可移植的 `LIKE`**：`LOWER(title) LIKE ? ESCAPE '!' OR LOWER(description) LIKE ? ESCAPE '!'`，
   绑定值在 Java 侧转小写并转义 `!`、`%`、`_`；
6. 所有筛选条件以 **AND** 组合，每个条件对应一个写死的 SQL 片段，值一律参数绑定；
7. 查询**最多两条语句**：一条 `COUNT(*)`，一条分页数据查询（总数为 0 时只执行 `COUNT`）；
   两条语句处于**同一个独立（`REQUIRES_NEW`）、只读、`REPEATABLE_READ` 的事务**中，**没有 N+1**；
8. 越界页返回 **200 + 空 `items`**，`totalElements`/`totalPages` 照常给出，**不是 404**；
9. 列表响应**不返回集合 ETag**；
10. 迁移 **V2** 只加两棵索引：`(updated_at DESC, id ASC)` 与 `(requester_id, updated_at DESC, id ASC)`。

## 理由

### 为什么这一阶段用 offset 分页

- **需求以「第几页」为单位。** 本阶段的界面与调用方心智都是页码 + 每页条数，
  `page`/`size` 与 `hasNext`/`hasPrevious`/`totalPages` 能直接表达它；
  cursor/keyset 表达不了「跳到第 5 页」，也天然给不出总数。
- **总数是产品需求。** 列表要显示「共 42 条」，就必须有一次 `COUNT(*)`。
  keyset 分页的优势在于避免深翻页，但它并不能省掉总数查询。
- **代价是明确的、可接受的。** offset 分页在深翻页时数据库仍要跳过前 N 行，
  `OFFSET` 越大越慢；并且并发写入会让「翻页过程中新插入的行」造成重复或跳行。
  本阶段的工单量级与页深都有限，且**每次请求都是独立一致视图**，
  重复/跳行只在跨越多次请求的翻页过程中才可能出现。
- **keyset 分页已明确列为后续工作**：届时需要 `(排序键, id)` 的复合游标与「上一页」的反向查询，
  属于独立的一次设计，不在本任务实现。

### 为什么排序必须走白名单

- **排序字段无法用参数绑定。** SQL 的 `ORDER BY` 不接受占位符，所以「列名」只能来自程序常量。
  任何形式的 `ORDER BY ` + 客户端字符串都是注入点，哪怕加了正则过滤也不该做。
- **做法是把「解析」与「拼接」分开**：客户端的 `"updatedAt"` 先经
  `TicketSortField.fromWire`（区分大小写，只认 4 个线上名称）变成枚举常量；
  拼 SQL 时只对枚举做穷尽 `switch`，输出写死的列名。
  解析失败的处理发生在应用层（400），根本到不了存储层。
- **穷尽 `switch` 还有编译期保护**：将来给枚举加一个常量，`switch` 会编译不过，
  迫使实现者显式决定新字段的 SQL 表示，而不是悄悄退化成「不认识的字段就不排序」。

### 为什么业务顺序要用 CASE

- `priority` 存的是 `VARCHAR`：`P1,P2,P3,P4` 的字典序碰巧等于业务顺序，但这是巧合而非契约；
- `status` 存的是 `VARCHAR`：字典序给出 `ASSIGNED, CLOSED, IN_PROGRESS, NEW, RESOLVED`，
  与生命周期顺序 `NEW → ASSIGNED → IN_PROGRESS → RESOLVED → CLOSED` **完全无关**；
- 因此用 `CASE priority WHEN 'P1' THEN 1 … END` 把枚举映射成序号再排序。
  序号来自编译期常量数组，`ELSE` 兜住理论上的未知取值（数据库 CHECK 已保证不会出现）。
- **被否决的替代方案**：新增一个冗余的排序列（如 `priority_rank SMALLINT`）并加索引。
  它能让优先级排序也走索引，但要改动 V1 已定的表结构、并要求所有写入路径维护排名；
  当排序字段只有两个、且它们的选择性很低时，收益不足以抵消复杂度。

### 为什么坚持「id ASC 兜底」

- 只有单一排序键时，并列行的相对顺序**由数据库实现决定**，SQL 标准不作任何承诺。
  并列在实际数据中很常见：同一批导入的工单 `updated_at` 相同、同优先级、同状态。
- 没有兜底键时，`LIMIT/OFFSET` 分页会**重复或漏掉**并列行 —— 这不是理论问题，
  而是「翻到第二页发现第一条和第一页最后一条相同」这类可复现的缺陷。
- 追加 `id ASC` 后顺序成为全序，分页因此自洽。集成测试里专门有一个用例：
  在并列极多的排序下逐页翻完，断言不重不漏。

### 为什么关键字搜索用可移植 LIKE

- **需求是「包含」而非「相关性排序」。** 用户要的是「标题或描述里出现这几个字」，
  LIKE 的语义刚好匹配，且行为完全可预测（不涉及分词、词干、停用词）。
- **可移植性**：`LIKE ... ESCAPE` 与 `LOWER()` 在 PostgreSQL 与 H2 的 PostgreSQL 兼容模式下语法一致，
  同一套 SQL 既能在本地集成测试里跑，也能在真实 PostgreSQL 上跑，
  不需要为测试环境写第二套实现。
- **大小写不敏感**由「列经 `LOWER()`、绑定值在 Java 侧 `toLowerCase(Locale.ROOT)`」实现，
  两侧都在小写域里比较。对 ASCII 与中文一致；不做数据库级 Unicode 折叠（见「重新评估条件」）。
- **通配符必须转义。** `%` 与 `_` 是 LIKE 的通配符，不转义就不是注入而是**语义被用户输入改变**：
  搜索 `"100%"` 会退化成「以 100 开头」，搜索 `"_"` 会匹配到几乎全部行。
  选择 `!` 作转义符（`%`、`_`、`!` 三个字符都可能出现在业务文本里，选哪个都一样，
  关键是**同时转义转义符自身**），并在 SQL 里显式声明 `ESCAPE '!'`。
  集成测试用「`%` 只命中 2 条而不是全部 8 条」「`!` 命中 G、H 而不是 F、H」这类断言锁定语义。
- **明确不做的**：完全不使用字符串拼接来构造模式，模式是**绑定值**，
  所以 `'; DROP TABLE tickets--` 只会变成一个「查不到任何东西」的字面量（有测试断言表仍然完好）。

### 为什么越界页不是 404、列表也没有 ETag

- **越界页是正常的翻页行为。** 客户端翻过头、或数据被删除导致页数变少，
  都不该被当成「资源不存在」；返回 200 + 空 `items` + 真实的 `totalElements`，
  客户端据此自行修正页码即可。404 会让调用方误以为写错了 URL。
- **集合没有单一版本号。** 给列表一个 ETag，等于隐含承诺「整页内容是一个可整体校验的表示」，
  而任何一条工单的变化都会改变页内容；客户端拿它做 `If-None-Match` 会得到大量无意义的失效。
  逐条的并发控制仍走单条读取的 ETag + 写请求的 `If-Match`（ADR 0003）。

### 为什么分页元数据在应用层推导

- 存储适配器只返回「当前页数据 + 总数」这一对事实；
  `totalPages`、`hasNext`、`hasPrevious` 是它们的**函数**，属于展示语义，多一层实现就多一处不一致。
- **`totalElements` 用 `long`，`totalPages` 也用 `long` 计算**：
  `totalElements / size` 在 `int` 域里做会溢出成负数，而「总数很大」恰恰是分页接口要面对的情况。
  `hasNext` 同样用 `long` 计算 `(page + 1) * size`，避免大页码下的溢出误判。

### 为什么 COUNT 与分页查询必须在同一个只读 REPEATABLE_READ 事务里

- **两条独立语句天然可能看到两个世界。** 总数与明细是先后发出的两条 `SELECT`。
  在默认的 `READ_COMMITTED` 下，每条语句各取一个新快照 —— PostgreSQL 文档明确如此，
  H2 的 `READ_COMMITTED` 同样是「每条语句看到最新已提交数据」。
  于是两条语句之间提交的写入会让响应自相矛盾：
  - 并发**插入**一条匹配记录：`totalElements` 是 5，`items` 却返回 6 行；
  - 并发**删除**一条匹配记录：`totalElements` 是 5，`items` 却只有 4 行。
  调用方据此算出的 `totalPages`、`hasNext` 全是错的，而且这类错误只在并发下偶发，极难排查。
- **因此列表查询跑在独立的只读 `REPEATABLE_READ` 事务里**：两条语句看到同一个已提交快照。
  实现上是 `TicketPersistenceConfiguration` 里的第二个 `TransactionTemplate`
  （**`PROPAGATION_REQUIRES_NEW`、`readOnly = true`、`ISOLATION_REPEATABLE_READ`**），只注入给 `search`。
- **「独立事务」明确指 `REQUIRES_NEW`，而不是默认的 `REQUIRED`。** `TransactionTemplate` 的默认传播行为是
  `PROPAGATION_REQUIRED`：它会**加入**调用方已经存在的那个事务。一旦加入，本模板的 `readOnly` 与隔离级别
  **都不会生效** —— 外层事务已经决定并设置好了连接上的只读标志与隔离级别，Spring 不会为参与其中的内层事务
  再改一次。此时若外层是默认的 `READ_COMMITTED`，COUNT 与分页查询就又各自取新快照，
  上面描述的自相矛盾会**静默回归**，而且只在「有人在事务里调用 search」时才出现。
  `REQUIRES_NEW` 让内层真正独立：**外层事务被暂时挂起**（不提交、不回滚，其连接仍被占有），
  内层用**另一条连接**开启新事务，内层结束后**外层被恢复**（绑定回原来那条连接与它未提交的状态）。
- **代价：嵌套调用时额外占用一条数据库连接。** 外层连接在外层事务结束前不会归还连接池，
  因此「在长事务里调用列表查询」会比平常多占一条连接。这也是本模板只用于一次列表查询、
  且查询本身只发两条语句的原因。
- **写路径刻意不跟着提升隔离级别。** 乐观并发靠的是「行锁 + 条件更新」这对显式 SQL（ADR 0002），
  与隔离级别无关；把写事务一起改成可重复读只会增加锁竞争与序列化失败风险。
  写事务模板保持默认传播、默认隔离级别，两个模板分开，改一个不会牵动另一个。
- **`readOnly = true` 不只是注释。** 它把「查询不写库」这条约定从代码纪律升级为事务级声明：
  驱动与数据库可以据此走只读路径，某些数据库还会拒绝该事务中的写入。
- **被否决的替代方案**：用 `COUNT(*) OVER ()` 把总数塞进分页查询的同一条语句。
  它确实只要一条语句，但**零行时拿不到总数**（窗口函数没有行就没有输出），
  还要为「越界页」和「空结果」额外分支；两条语句 + 快照隔离更直白，也更容易验证。
- **代价**：可重复读事务对数据库的版本清理压力略高于读已提交。这里的只读事务只包含两条语句、
  存活时间极短，影响可以忽略。
- **确定性验证（两种场景）**：
  1. **无外层事务**：集成测试用 `DataSource` 代理把钩子挂在「COUNT 已完成、分页查询尚未下发」
     这一点上（拦住 `prepareStatement`），由另一个真实连接并发插入或删除并**等待其提交**，
     然后断言总数与明细仍来自同一快照；事务结束后再查一次，证明那次并发写入确实发生了
     （控制断言，避免测试空转）；
  2. **嵌套在外层事务里**：另有一组用例先开启一个默认读写的外层事务、在其中执行 SQL 让外层连接真正绑定，
     再调用 `search`，断言：搜索走的是**另一条连接**、该连接上**确实**被设置为只读与可重复读、
     搜索**看不到外层未提交的写入**、搜索结束后外层**绑定回原来那条连接**且仍能继续读写、
     外层回滚**不会**牵连搜索、并发写入仍被精确卡在 COUNT 与分页查询之间且快照保持一致。
  两组用例全程没有 `sleep`，所有等待都有超时。
  把 `REPEATABLE_READ` 去掉后第一组的三条断言会立即失败（已实测：总数 5、明细只有 4 行）；
  把传播行为改回默认的 `REQUIRED` 后**第二组 5 个用例全部失败**（已实测：内层搜索看到外层未提交的行，
  得到 6 而不是 5）。

## 影响

正面：查询接口的形状与产品心智一致（页码 + 总数）；排序无法被注入且新增字段有编译期保护；
排序业务顺序与领域枚举一致而非依赖字典序；并列行分页不重不漏；
关键字语义可预测、通配符不作妖；一次查询最多两条语句、零结果只发一条；
总数与明细永远来自同一个数据库快照，响应不可能自相矛盾；
列表与单条读共用同一个响应表示（`TicketResponse`），客户端只需一套解析代码。

代价：深翻页会随 `OFFSET` 增大而变慢；`COUNT(*)` 每次都要执行；
包含搜索无法使用 B 树索引，本阶段是**全表扫描 + 过滤**；
大小写不敏感依赖 `LOWER()`，对需要完整 Unicode 折叠的语言不完整；
在已有事务中调用列表查询时会**额外占用一条数据库连接**（`REQUIRES_NEW` 挂起外层但仍持有其连接）。

## 索引决策（迁移 V2）

| 索引 | 服务的查询 | 理由 |
| --- | --- | --- |
| `idx_tickets_updated_at_id (updated_at DESC, id ASC)` | 默认排序 | 列顺序与方向同排序键完全一致，可直接顺序扫描，无需为并列值再排序 |
| `idx_tickets_requester_updated_at_id (requester_id, updated_at DESC, id ASC)` | 「我提交的工单」+ 默认排序 | 最典型的等值筛选，且几乎总与默认排序同时出现；等值列在最左，其余列提供有序性 |

**明确不添加的候选**（避免无理由堆索引）：

- `(category, …)`、`(priority, …)`：选择性太低（5 个、4 个取值），
  优化器通常宁可走默认排序索引再过滤，多维护一棵索引只增加写入放大；
- `status`、`assignee_id`：V1 已有 `(status, updated_at)` 与 `(assignee_id, status)`，等值筛选直接复用；
- `(created_at DESC, id)`：V1 的 `(created_at)` 已能提供按创建时间定位的能力，本阶段不叠加；
- **关键字包含搜索**：`LIKE '%…%'` 的前缀不确定，B 树索引无法使用，本阶段接受全表扫描。

## 重新评估条件

1. 单表工单量增长到深翻页成为瓶颈（例如 `OFFSET` 达到数万），届时改用 keyset/游标分页；
2. 需要「按相关性排序」或数据量使 `LIKE` 全表扫描不可接受，届时在 PostgreSQL 上评估
   **全文检索（`tsvector`）或 `pg_trgm` 的 GIN 索引** —— 这属于后续优化，本任务明确不实现；
3. 需要完整 Unicode 大小写折叠（例如土耳其语 `İ/i`），届时把折叠下沉到数据库并使用 `ILIKE`
   或数据库侧的 collation；
4. 出现按 `category`/`priority` 单独筛选的大批量查询，并证明索引确实能被使用，届时再补组合索引；
5. 排序字段增加到需要动态生成的规模，届时评估「排序字段注册表 + 每字段固定的 SQL 片段」的做法；
6. 在真实 PostgreSQL 上观察到可重复读事务的代价（版本清理、长事务告警）或序列化失败，
   届时评估改用 `SNAPSHOT` 隔离级别或单单据 CTE 方案。
