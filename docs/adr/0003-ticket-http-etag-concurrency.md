# ADR 0003：工单 HTTP 接口的 ETag 乐观并发协议

- 状态：已接受
- 日期：2026-09-13
- 决策范围：工单 REST 接口的资源表示与并发控制协议

## 背景

工单聚合与应用层已经确立了乐观并发契约：每次成功更新版本严格加 1，
`update` 是原子的 compare-and-set，版本过期必须与「记录不存在」区分开（ADR 0002）。

现在要把这套语义暴露成 HTTP。需要回答四个问题：

1. 版本放在哪里传递？
2. 版本过期用什么状态码？
3. 生命周期操作怎么映射成资源操作？
4. HTTP、应用层、领域层各自负责什么？

## 决策

1. 版本作为资源的 **ETag** 暴露，写请求通过 **`If-Match`** 携带期望版本，请求体中不出现 `expectedVersion`；
2. 版本冲突返回 **412 Precondition Failed**；缺少 `If-Match` 返回 **428 Precondition Required**；
3. 生命周期操作使用**显式命令端点**（`/assign`、`/reassign`、`/start`、`/resolve`、`/close`），
   用 `POST` 而不是对资源做 `PATCH`；
4. 三层职责严格分离：HTTP 只做映射与转换，应用层做编排与并发，领域层做规则裁决。

## 理由

### 为什么版本放在 ETag / If-Match，而不是请求体

- **ETag 就是为这件事设计的。** RFC 9110 的 `If-Match` 语义正是「只有当前表示仍是我读到的那一版，
  才执行这个请求」，与 compare-and-set 一一对应。把版本塞进请求体等于重新发明一个更弱的机制。
- **避免表达重复。** 同一个版本号若既在响应头又在响应体，就有两个真相来源；若只在请求体出现，
  则 GET 的响应里必须额外放一个纯技术字段，且客户端容易忘记回传。
  现在的做法是：**响应头 `ETag` 与响应体 `version` 同时给出且永远一致**（有测试锁定），
  写请求则只认 `If-Match`。
- **可以走通用 HTTP 基础设施。** 缓存、代理、条件请求、客户端库对 ETag 有一等支持；
  自定义字段则不会得到任何工具支持。
- **防止「忘记带版本」导致的静默覆盖。** 如果版本可选，遗漏就会退化成 last-write-wins；
  强制 `If-Match` 把这种遗漏变成 428 显式失败。

### 为什么版本冲突用 412

- 412 的定义就是「一个或多个前置条件在服务器上求值为假」，而版本不匹配正是这种情况；
- 与 409 Conflict 区分开：409 在本项目用于**业务状态冲突**（非法状态转换、相同处理人）与
  唯一键冲突（工单已存在）。若把版本冲突也塞进 409，客户端就无法区分
  「我拿的是旧版本，重读即可重试」和「这个状态本来就不允许该操作」——前者可自动重试，后者不可；
- 与 428 配对使用：428 表示「你没给前置条件」，412 表示「你给的前置条件不成立」，
  两者共同构成完整的前置条件协议。

### 为什么生命周期操作使用显式命令端点

- **状态转换不是资源的部分更新。** `resolve` 必须同时写入处理结论、`resolvedAt` 与 `updatedAt`，
  并校验当前状态是 `IN_PROGRESS`。用 `PATCH {"status":"RESOLVED"}` 表达，
  既无法要求 `resolution` 必填，也无法表达「当前状态必须是什么」，只能退化成服务端猜意图。
- **命令名即业务动作。** `/assign`、`/reassign`、`/start`、`/resolve`、`/close` 与领域方法一一对应，
  接口读起来就是业务语言，审计、授权与埋点也能按动作维度切分（后续 FD 需要时）。
- **幂等语义清晰。** 这些动作都是「重复执行会因状态机而失败」而不是「重复执行无害」，
  因此用 POST（非幂等）而非 PUT 更诚实。
- **与领域状态机同构。** 状态机是「当前状态 + 动作 → 新状态」，端点设计保持同样的形状，
  用例服务里就是一次直白的调用，不需要在 HTTP 层做任何状态判断。

### 三层职责

| 层 | 负责 | 明确不负责 |
| --- | --- | --- |
| HTTP（`com.flowdesk.bootstrap.ticket`） | URL 与方法映射、DTO ↔ 命令/视图转换、`If-Match` 解析与 `ETag` 输出、异常到状态码/错误码映射 | 不注入 Repository/JdbcClient/领域聚合；不做业务状态判断；不读写数据库 |
| 应用层（`com.flowdesk.application.ticket`） | 用例编排、版本比对、事务边界的声明式表达、错误码语义（`INVALID_COMMAND`/`TICKET_NOT_FOUND`/`TICKET_VERSION_CONFLICT`） | 不认识 HTTP；不生成标识与时间（走端口） |
| 领域层（`com.flowdesk.domain.ticket`） | 状态机与全部不变式：允许哪些转换、字段必填与长度、时间链、状态与可选字段共存 | 不认识 HTTP、Spring、数据库；不读系统时钟 |

领域规则**不会**被复制成 Controller 的业务判断：Bean Validation 只拦「形状明显不合法」的输入
（空值、超长、非法枚举），语义是否成立一律由聚合裁决，领域错误码原样向上传递。

## 影响

正面：并发协议标准且可被通用工具理解；两层错误语义清晰（重读可重试 vs 状态不允许）；
接口形状与领域状态机同构；分层职责可机械校验。

代价：客户端必须先 GET 拿到 ETag 再写（这是乐观并发的固有成本，也是它的价值）；
一个业务动作一个端点，端点数量随动作增长。

## 重新评估条件

1. 出现需要批量修改、部分更新语义的接口（例如批量改派），届时需要评估 PATCH 与 JSON Merge Patch；
2. 客户端无法使用 HTTP 头（例如某些 MQ 或内部 RPC 桥接），需要另设版本传递通道；
3. 需要引入缓存层，届时 ETag 的生成策略（是否仍等于版本号）需要重新评估；
4. 动作数量增长到端点爆炸的程度，届时考虑用一个带判别字段的命令端点收敛。
