# ADR 0005：知识文档上传与原始文件存储

- 状态：已接受
- 日期：2026-09-13
- 决策范围：知识文档（RAG 第 1/6 步）的元数据建模、原始内容存储、上传时序与失败补偿

## 背景

RAG 链路的第一步不是解析，而是**把一个文件安全地收进来**。在解析、切片、向量化之前，
必须先回答一组更基础的问题：

1. 元数据与原文件分别放在哪里？
2. 原文件用什么方式存？为什么不是数据库？
3. 上传过程中怎么防止把服务器写坏、写满、写到别的地方去？
4. 文件已经落盘、元数据还没写进去时失败，会留下什么？
5. 摘要（SHA-256）在什么时候算，为什么？

本任务只做「收进来 + 查得到」，**不做**解析、切片、Embedding、向量库与检索。

## 决策

1. **元数据进数据库（`knowledge_documents` 表），原始文件走内容存储端口**
   （`KnowledgeDocumentContentStore`），当前实现是本地文件系统适配器；
2. **内容键由文档标识派生**（`kdoc-<uuid>`），由服务端生成，**原始文件名永远不参与路径拼接**；
3. **流式处理**：固定缓冲区边读边算 SHA-256，绝不把文件整体载入内存，也不使用
   `MultipartFile.getBytes()`；
4. **大小限制按实际读取到的字节数判断**（默认 20 MiB，可配置），不信任
   `Content-Length` / `MultipartFile.getSize()` / 容器配置；
5. **先临时、后原子**：内容先写到存储根目录下的临时文件，全部校验通过后
   `ATOMIC_MOVE` 到最终位置；不支持原子移动时安全降级为同目录移动；**绝不覆盖已有对象**；
6. **任何失败都清理临时文件**；
7. **上传时序固定**，且**文件复制期间不持有数据库事务**：内容落盘 → 元数据单条 INSERT；
8. **元数据写入失败时补偿删除内容**（`delete(contentKey)`），补偿失败只可能留下孤立文件；
9. 文档只有 `UPLOADED` 一个状态，本阶段不可变、无更新入口。

## 理由

### 为什么元数据进数据库、原文件走内容存储端口

- **两者的访问模式完全不同。** 元数据要按条件查询、将来还要分页与过滤 —— 这是关系数据库的强项；
  原文件是不可变的大二进制块，只按不透明键读写 —— 这是对象存储/文件系统的强项。
  把 20 MiB 的文件塞进数据库的 `bytea`，会让备份、迁移、VACUUM、连接池全都被拖累。
- **端口隔离让替换成本可控。** 应用层只认识 `store` / `delete` 两个方法，
  因此将来换成 MinIO/S3 是**加一个适配器**，而不是改用例；
  这也是内容键必须保持**不透明**的原因：调用方一旦开始解析它，替换就成了破坏性变更。
- **对外契约里不出现内容键。** `KnowledgeDocumentView` 里根本没有这个字段（有测试用反射锁定），
  所以「响应绝不泄漏 contentKey」是结构性成立的，而不是靠组装响应时的纪律。

### 为什么默认先提供本地文件系统适配器

- **本阶段只需要「存得住、取得回、删得掉」。** 引入对象存储意味着额外的部署依赖
  （MinIO/S3、凭证、网络），而当前没有任何功能需要它。
- **本地文件系统足以验证全部关键语义**：原子落盘、摘要、大小限制、失败清理、路径收敛 ——
  这些语义在换成对象存储后依然存在（只是表现形式不同）。
- **它同样能暴露真实问题**：临时文件与最终对象必须在同一个文件系统内才能原子移动，
  这条约束在本地适配器上就已经体现了。
- 明确边界：**它只是当前适配器**，不是架构承诺；替换点在端口，不在用例。

### 为什么原始文件名不参与路径

- **文件名是客户端完全可控的输入。** `../../etc/cron.d/x`、`C:\fakepath\a.txt`、
  含 NUL 或换行的名字都能出现在 multipart 里。任何「用文件名拼路径」的实现，
  第一个恶意请求就能写到存储根目录之外。
- **做法是让路径与文件名解耦**：内容键 = `kdoc-<文档标识>`，标识由服务端生成，
  客户端无法影响；文件名只作为**元数据**保存与展示。
- **还有两道额外的闸门**：应用层先按 `/` 与 `\` 取最后一段（兼容浏览器传来的伪路径），
  领域层的 `OriginalFilename` 值对象再拒绝任何含分隔符或控制字符的值 ——
  因此**存进数据库的文件名本身就是安全的**，将来的任何展示、日志或下载接口都不会被它带偏。
- **解析路径时仍做包含性检查**：内容键会从数据库读回来，因此适配器在字符集白名单之外，
  还会验证解析结果必须仍在存储根目录内。两道检查都失败才可能越界，而越界只会得到一个固定的服务端错误。

### 为什么流式计算 SHA-256

- **完整性证据必须来自真实字节。** 摘要同时用于去重识别与内容校验；
  如果先落盘再回头读一遍计算，就多了一次完整 I/O，而且中间窗口里的磁盘错误不会被发现。
- **不把文件载入内存是硬要求。** 上传大小由客户端决定，一次 20 MiB 的请求乘以几个并发就足以压垮堆；
  而「一边复制一边摘要」与「一次读完再摘要」在性能上并没有代价 —— 摘要本来就是顺序计算。
- **顺手解决了空文件**：复制循环结束时字节数为 0 就直接在**移动之前**拒绝，
  因此不会先落一个空对象、再回头删掉它。
- 该摘要是**普通索引而非唯一约束**：相同内容允许作为不同逻辑文档上传，
  唯一化会把「同一份文件两个用途」变成不可表达的语义。

### 为什么文件复制期间不持有数据库事务

- **上传是慢操作。** 一条 20 MiB 的上传可能持续数秒；如果这期间占着事务，
  就等于用客户端的网速去占用连接池与数据库资源。事务应当只包住真正需要原子性的那一条 INSERT。
- **顺序是「先内容、后元数据」，而不是反过来。** 反过来会先产生一条指向不存在内容的记录，
  那是最坏的结果：**任何读到它的人都会以为内容存在**。
  按当前顺序，最坏情况只是一个没人引用的文件。
- 内容写入本身是原子的（临时文件 → 原子移动），因此不需要靠数据库事务来保证它的一致性。

### 补偿机制与崩溃边界（如实说明）

| 失败点 | 后果 | 处理 |
| --- | --- | --- |
| 校验失败（标题/文件名/格式/大小） | 没有任何副作用 | 不打开文件、不调用存储 |
| 内容写入失败（含超限、空内容） | 临时文件被清理 | 适配器 `finally` 清理，异常向上传递 |
| 内容已落盘、元数据 INSERT 失败 | **调用 `delete(contentKey)` 补偿** | 补偿基于由标识派生的内容键，不可能误删其它文档 |
| 补偿删除也失败 | 可能留下**孤立文件** | 对外仍是固定的 500；**绝不留下指向不存在内容的元数据** |
| 进程在「内容已落盘」与「元数据 INSERT」之间崩溃 | 可能留下**孤立文件** | **本阶段不实现清理任务**，如实记录为已知边界 |

- 最后一行是**真实存在**的边界，不做粉饰：崩溃无法被应用层捕获，因此只能靠兜底机制解决。
- 后续会引入「扫描内容目录、删除无元数据引用的对象」的清理任务；**本任务不实现**，
  也不假装已经解决。当前的取舍是：宁可留下没人引用的文件，也绝不留下指向不存在内容的记录。

## 影响

正面：上传路径的每一步都可验证（落盘对象、摘要、大小、临时文件清理都能在文件系统上观察到）；
客户端输入无法影响存储位置；失败路径不会产生「半条」数据；
内容存储可替换而不触及用例；响应契约里不出现任何内部坐标。

代价：多了一套需要独立备份的存储（内容目录与数据库必须一起备份，否则会互相失去意义）；
孤立文件需要后续清理任务；本地适配器在单机上不提供横向扩展与多副本冗余
（这些是对象存储的职责，属于替换适配器时的事）。

## 本任务明确不做的事

- PDF/DOCX 正文解析、文档切片、Embedding、pgvector 或其它向量库、RAG 检索；
- 文档列表、下载、删除与版本更新接口；
- 权限、租户、伪造的用户身份请求头；
- 孤立文件的定时清理；
- MinIO/S3 适配器（端口已经就位，替换时不需要改应用层）。

## 重新评估条件

1. 需要多副本、跨机共享或对象生命周期策略时，引入 MinIO/S3 适配器；
2. 单文件上限或日上传量增长到本地磁盘不可接受时，评估分片上传与直传对象存储；
3. 出现「同一内容多文档」的去重需求时，再讨论内容寻址存储（届时要重新审视内容键的生成方式）；
4. 解析阶段引入后，需要为「解析中/已解析/解析失败」增加状态与状态流转时，
   本节的状态机（当前只有 `UPLOADED`）需要重新设计。
