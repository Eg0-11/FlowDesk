# ADR 0008：查询向量与 pgvector 相似度检索（RAG 4/6）

- 状态：已接受
- 日期：2026-09-15
- 决策范围：知识检索（RAG 第 4/6 步）的查询向量生成、pgvector 余弦检索、
  引用结果与 HTTP 契约

## 背景

RAG 第 3 步把切片变成了向量并落进 pgvector，但那些向量此前<b>只写不读</b>。
第 4 步要回答的是：**把一段用户问题变成可审计的引用结果** ——
用户问题 → 查询向量 → 余弦检索 → 带编号与分数的命中切片。

具体问题：

1. 查询向量能不能复用文档侧的 Embedding 端口？
2. 查询向量能不能用 DeepSeek 生成？
3. 检索为什么不用 Spring AI 的 `PgVectorStore`？
4. 相似度、距离与排序怎么写，才能既正确又能用上 HNSW 索引？
5. 「库里的向量是不是当前模型的」怎么保证？
6. 分数相同时顺序怎么稳定，引用编号怎么定？
7. 模型调用与 SQL 的事务边界在哪？
8. 这一阶段<b>不</b>做什么？

本任务**不做**：调用 DeepSeek Chat、生成自然语言答案、Rerank、全文检索、混合检索、
接入 Agent/MCP、新增数据库迁移、修改索引状态机。

## 决策

1. **查询与文档共用同一个模型与同一份描述符，但使用不同的 `textType`**：
   文档侧 `document`（`KnowledgeEmbeddingPort`），查询侧 `query`
   （独立的 `KnowledgeQueryEmbeddingPort` + `DashScopeKnowledgeQueryEmbeddingAdapter`）；
2. **查询向量只能由 DashScope 生成**，不能换成 DeepSeek：它必须与库里的文档向量处于
   **同一个向量空间**；
3. **不使用 Spring AI 的 `PgVectorStore`，不自动建表**：检索必须同时满足
   「只检索 `INDEXED` 文档」「描述符精确匹配」「向量摘要与切片一致」三条约束，
   这些只能由业务表之间的连接表达；
4. **一条只读 SQL**完成检索：距离算子 `<=>` 计算相似度、`>= minScore` 含边界过滤、
   `ORDER BY 距离 ASC` 作为第一排序键并带确定性 tie-break、`LIMIT ?` 绑定 topK；
5. **写入与查询共用同一个向量字面量序列化工具**（`PgVectorLiteral`），
   保证同一个数值在两条语句里被解析成同一个向量；
6. **结果契约由用例服务校验、由 SQL 保证**：应用层<b>不</b>排序、<b>不</b>去重、
   <b>不</b>截断，发现违反契约就当作内部错误；
7. **引用编号按最终顺序确定为 `K1`、`K2`……**，`rank` 从 1 连续递增；
8. **检索是只读的**：不修改文档版本/状态/失败码，也不写入或删除任何向量；
   因此检索失败没有 `failureCode`，也不会留下 `INDEX_FAILED`。

## 理由

### 为什么查询与文档必须同模型、不同 textType

- **同一个向量空间**：余弦相似度只在同一模型、同一维度、同一语义约定下才有意义。
  用另一个模型生成的查询向量去比较库里的文本向量，得到的相似度是噪声 ——
  而且不会报错，只会让召回结果变得莫名其妙。
- **不同 `textType`**：DashScope 的检索语义约定要求文档侧标注 `document`、查询侧标注 `query`。
  两侧混用会让相似度整体偏斜（非对称检索任务里这是已知现象）。
  因此本项目把差异放在**结构**上：两个独立端口、两个独立适配器，
  而不是一个布尔参数 —— 后者会让「同一次批量里混着两种语义」成为可能。
- **为什么不用一个端口加参数**：`KnowledgeEmbeddingPort` 的契约是「批量、文档语义」，
  查询是「单条、查询语义」。把它们塞进同一个接口，调用方就必须自己记住传对参数，
  而契约本身不再能表达这条约束。

### 为什么查询向量不能交给 DeepSeek

- DeepSeek 的公开接口提供的是 Chat Completions，本项目通过 OpenAI 兼容传输使用它（ADR 0001）；
  它<b>不</b>提供与本项目文档向量同一空间的 Embedding 服务。
- 「能生成向量」和「能生成<b>可比较的</b>向量」是两件事：换了模型就必须重算全部文档向量
  （维度或语义空间变化即必须重算，见 ADR 0007 的重新评估条件）。
- 因此本阶段的边界很清楚：**Chat/Agent 走 DeepSeek，Embedding 与检索走 DashScope + pgvector**。

### 为什么不用 PgVectorStore（检索侧）

- **没有业务过滤维度**：通用表只有 `id/content/metadata/embedding`，
  无法表达「只检索已索引文档」「描述符必须匹配」「向量摘要必须等于切片摘要」；
- **过滤放在应用层就晚了**：先把 topK 交给通用 store、再在内存里剔除不匹配的行，
  会得到「条数不足」甚至「全是应该被排除的命中」的结果，而调用方无法察觉；
- **事务边界冲突**：本项目要保证「模型调用不持有数据库连接、检索只读」，
  通用 store 的 API 形态不允许这种精确控制；
- **表结构所有权**：本项目的 DDL 全部在 Flyway 里，`initialize-schema` 必须关闭
  （见 ADR 0007）。

因此检索用的是一条**自定义只读 SQL**（`KnowledgeRetrievalSql`）。

### 余弦距离、分数与 HNSW 排序

- pgvector 的 `<=>` 是**余弦距离**（`1 - 余弦相似度`），因此
  **分数 = `1 - (embedding <=> query)`**，落在 `[0, 1]`（向量非零时）。
- 排序必须写成：

  ```sql
  ORDER BY e.embedding <=> ?::vector ASC, e.document_id ASC, e.chunk_index ASC
  ```

  - **第一排序键必须是距离表达式本身**：V6 建的是 HNSW `vector_cosine_ops` 索引，
    只有 `ORDER BY <列> <=> <常量/参数>` 这种形态才能让规划器选择索引扫描。
    写成 `ORDER BY (1 - distance) DESC` 或把距离投影成别名再排序，都会退化成
    全表扫描 + 排序 —— 结果仍然正确，但数据量一大就不可用，而且**不会报错**。
  - **tie-break 必须存在**：距离完全相同的两行，数据库没有义务保持稳定顺序。
    引用编号是按最终顺序生成的，顺序抖动会让同一份数据在两次检索里给出不同的 `K1`。
- 阈值过滤写成 `>= ?`（含边界）：`minScore` 的语义是「不低于此值即算命中」，
  用 `>` 会把恰好等于阈值的命中悄悄丢掉。

### descriptor 与 SHA-256 过滤

- **描述符精确匹配（文档行 + 向量行各一次）**：文档上记录了它被索引时用的
  provider/model/dimensions，向量行也各记了一份。检索要求两者都等于当前配置，
  这样「换了模型但还没重算旧向量」的历史数据不会被混进结果里。
- **摘要一致（`c.sha256 = e.chunk_sha256`）**：向量是**当时的文本**的函数。
  如果切片在写入向量之后被换过（重新解析、人工改数据），引用出去的内容与向量描述的
  就不是同一段文本 —— 这类错配不会报错，只会让引用看起来「有依据」。
  连接条件把这条证明交给数据库，而不是靠应用层抽查。

### 稳定 tie-break 与 citationId

- `citationId`（`K1`、`K2`……）是**给调用方用的**：答案里引用 `K1`，就能回到具体的
  文档、版本与切片。因此它必须与「最终返回顺序」一致，而不是与数据库的物理顺序一致。
- 顺序完全由 SQL 决定（分数降序 → documentId 升序 → chunkIndex 升序）；
  用例服务只按返回顺序编号，<b>不</b>重排。
- **用例服务为什么拒绝而不是修正**：如果适配器返回了乱序、重复或超过 topK 的结果，
  排序/去重/截断都会把「适配器坏了」这个真实缺陷掩盖成「结果看起来正常」。
  因此契约被破坏时统一以内部错误失败，让问题在测试与告警里暴露。

### 模型调用与 SQL 的事务边界

- **模型调用不持有数据库连接**：查询向量生成发生在任何 SQL 之前，且不在事务里；
- **检索是一条单语句的只读查询**：不开显式事务、不加 `FOR UPDATE`、不写任何表 ——
  单条语句本身就构成一个原子快照，无需更长的事务边界；
- **没有跨模型调用的事务**：不会出现「等上游响应时占着连接」的情况。

### 数量、长度与阈值都来自配置

- `flowdesk.knowledge.retrieval` 提供 `max-query-code-points`、`default-top-k`、
  `max-top-k`、`default-min-score`，装配期校验（`1 <= default-top-k <= max-top-k <= 50`；
  阈值必须是 0..1 的有限数值）；
- 应用服务只接收纯 Java 数值，不认识 Spring 配置类型；
- `topK` 与 `minScore` 可以由请求覆盖（在配置范围内），**上限与 query 长度上限不能**。

## 失败语义

| 失败点 | 数据库 | 对外 |
| --- | --- | --- |
| query 缺失/空白/超长/含控制字符，topK 或 minScore 越界 | 无任何访问 | 400 `INVALID_REQUEST`（固定 detail「检索请求不合法」） |
| 未启用向量化 | 无任何访问（**不调用模型、不读向量表**） | 503 `KNOWLEDGE_EMBEDDING_DISABLED` |
| 上游超时/限流/连接失败/5xx | 只读，无变化 | 502 `EMBEDDING_PROVIDER_ERROR` |
| 模型响应结构非法 / 查询向量非法 / 数据库检索失败 / 结果契约被破坏 | 只读，无变化 | 500 `INTERNAL_SERVER_ERROR` |
| 没有命中 | 只读，无变化 | **200 + 空 `citations`**（不是 404） |

- 错误响应一律不含 query、向量、SQL、连接串、用户名、密码或异常类名；
- 检索是只读操作，因此响应里<b>没有</b> `failureCode`，也不存在「检索失败留下失败态」这回事。

## 已知边界（如实记录）

1. **不做 Rerank**：本阶段只按向量相似度排序。Rerank（例如用上游 rerank 模型或 LLM 重排）
   是独立能力，会改变「分数」的语义，需要单独设计；
2. **不做混合检索**：没有 BM25 / 全文检索 / `pg_trgm` 的融合，纯向量召回；
3. **不生成答案**：接口只返回引用片段，不调用 Chat 模型、不拼接自然语言回答；
4. **没有任意切片读取接口**：不提供「按 documentId + chunkIndex 直接取切片」的接口 ——
   切片内容只能通过检索返回，且受 `topK` 与 `minScore` 限制；
5. **HNSW + 过滤的召回边界**：pgvector 的 HNSW 索引扫描在带过滤条件时是<b>后过滤</b>，
   极端情况下可能返回少于实际匹配数的行（`iterative scan` / 提高 `hnsw.ef_search`
   属于调优手段，本阶段未启用，也未做压测）；
6. **没有分页**：一次检索最多 `max-top-k`（默认 20）条，不提供游标翻页；
7. **PostgreSQL/DashScope 未在本机验证**：本机没有 Docker 与 `DASHSCOPE_API_KEY`，
   pgvector 相关断言由 Testcontainers 集成测试覆盖（无 Docker 时**跳过**并标注
   `POSTGRESQL_PGVECTOR_IT=NOT_RUN`），真实上游标注 `DASHSCOPE_LIVE=NOT_RUN`。

## 影响

正面：检索链路完全纵向打通（问题 → 向量 → 相似度 → 引用）；回答「哪一段最相关」时
有可复核的分数、文档版本与切片摘要；查询向量与文档向量同模型同维度；过滤条件全部下推到 SQL，
应用层不做任何「悄悄修正」；默认环境仍然零依赖可启动（检索接口返回 503）。

代价：多一条外部依赖路径（查询也要调用上游）；检索质量完全取决于向量模型与阈值配置，
没有重排兜底；相似度阈值需要按语料调参（默认 0.30 是保守值，宁可多召回）。

## 重新评估条件

1. 召回质量不足时：先评估阈值与 `top-k`，再评估引入 Rerank（届时需要区分「召回分」与「重排分」）；
2. 数据量增大后出现「带过滤条件召回不足」：启用 HNSW 迭代扫描或调高 `ef_search`，
   并按真实规模压测；
3. 需要关键词精确匹配（编号、错误码）时：引入 PostgreSQL 全文检索与混合打分；
4. 需要引用到答案时（RAG 5/6、6/6）：在检索之上接入 Chat 模型，并保持「引用只来自检索结果」；
5. 更换向量模型时：查询与文档必须同时切换，并重算全部向量（见 ADR 0007）。
