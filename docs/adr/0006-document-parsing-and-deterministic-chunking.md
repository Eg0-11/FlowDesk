# ADR 0006：文档解析与确定性切片

- 状态：已接受
- 日期：2026-09-14
- 决策范围：知识文档（RAG 第 2/6 步）的解析链路、状态机、切片算法、事务边界与失败补偿

## 背景

RAG 第 1 步解决了「把文件安全地收进来」。第 2 步要回答的是：**怎么把不可信的文件变成
可用的纯文本片段，并且这件事必须可重复、可并发、可失败、可重试。**

具体要回答的问题：

1. 用什么解析 PDF/DOCX？为什么不自己写、也不让 Tika 自动探测格式？
2. 解析结果怎么切？为什么必须**确定性**？
3. 解析与切片要不要放在数据库事务里？
4. 「切片写入」与「文档状态变成已解析」能不能分开做？
5. 解析失败、写库失败、进程崩溃分别会留下什么？
6. 状态机为什么需要 CAS，而不是「先查再改」？

本任务**不做**：Embedding、向量库、检索增强、Agent、MCP、消息队列、异步任务、OCR、
前端、权限与 Docker。

## 决策

1. **解析器采用 Apache Tika 3.x**（`tika-core` + `tika-parsers-standard-package`），
   版本由根 pom 的单一属性 `tika.version` 锁定；**不使用 `tika-app`**（那是命令行工具，
   会把大量与解析无关的依赖带进运行时）；
2. **解析器由服务端保存的 `DocumentFormat` 直接指定**（PDF → PDFBox、DOCX → POI OOXML），
   **不做二次自动探测**；Markdown/Text 不经过解析框架，直接严格 UTF-8 解码；
3. **解析适配器放在 `flowdesk-infrastructure`，切片器藏在应用层端口之后**
   （`DocumentTextParser` / `DocumentChunker`），应用层不出现任何 Tika/POI/PDFBox 类型；
4. **切片是确定性的、按 Unicode code point 计数的**，边界优先级为
   段落 > 句末标点 > 空白 > 硬切，并带可配置的重叠；
5. **解析与切片全程不持有数据库事务**；
6. **「完成解析」是一个原子端口方法**：删除旧切片、插入新切片、更新为 `PARSED`、版本加 1
   在**同一个事务**里完成；
7. **状态机用 CAS（行锁 + 带版本条件的 UPDATE）**：`UPLOADED`/`PARSE_FAILED` →
   `PARSING` → `PARSED`/`PARSE_FAILED`，并发领取只有一个赢家；
8. **失败补偿把文档落成 `PARSE_FAILED`**（可重试），补偿失败只作为 suppressed 保留；
9. **解析是同步完成的**：HTTP 请求返回时切片已经落库，因此接口返回 200 而不是 202。

## 理由

### 为什么用 Tika，而不是自己写解析器

- **PDF 与 DOCX 是两套复杂规范。** PDF 有自己的对象模型、交叉引用表、内容流与字体编码；
  DOCX 是 OOXML 包（ZIP + 多份 XML + 关系表）。自己写解析器不是「几十行代码」，
  而是要维护一套规范实现，且必然在真实文档上表现更差。
- **Tika 提供的是「解析器选择 + 统一 SAX 事件」这一层**，而这正是我们需要的：
  我们只需要**纯文本**，不需要结构化转换（因此不用 Tika 的 `AutoDetectParser` 自动探测，
  也不用它的 `BodyContentHandler` 之外的任何高级特性）。
- **风险被隔离在适配器里。** 应用层只认识 `DocumentTextParser` 这一个接口，
  将来换成别的解析库（或自研 PDF 解析）只影响一个类。

### 为什么由服务端声明格式，而不是让 Tika 探测

- **上传阶段已经做过一次权威识别**（扩展名 + 声明类型 + 文件头 + UTF-8/NUL 校验），
  结果已经落库。解析阶段再探测一次，只会得到「同一份文件两条结论」这类难以排查的分歧：
  例如某个 `.docx` 上传时按 ZIP 容器收下，解析时被探测成别的 OOXML 类型。
- **探测本身是攻击面。** 让解析库根据内容挑选解析器，等于把「用哪个解析器的决定权」
  交给文件内容；显式指定解析器后，攻击者只能影响「同一个解析器怎么处理坏输入」，
  而不能让它去执行一条我们没预期的解析路径。
- **代价是「声明与内容不符」必须显式处理**：解析前先校验文件头
  （PDF 必须 `%PDF-`、DOCX 必须是 ZIP），不符即 `UNSUPPORTED_DOCUMENT_CONTENT`，
  而不是含糊的「解析失败」。

### 为什么按 code point 而不是 char 切片

- Java 的 `String.length()` 数的是 UTF-16 单元：一个 emoji（代理对）算 2。
  按它切片会在中间切断代理对，产生**非法字符串**——数据库存得进去，JSON 也可能返回，
  但任何后续处理（向量化、检索、展示）都会遇到半个字符。
- 因此内部把文本转成 `int[]`（每个元素一个 code point），只在最后拼回字符串；
  领域层的 `KnowledgeDocumentChunk` 还会**再算一遍**并拒绝不一致的计数，
  把「有人偷偷用 `String.length()`」这件事变成构造期错误而不是脏数据。

### 为什么切片必须确定性

- **重新解析会替换切片。** 如果切片依赖时间、随机数、`HashMap` 迭代顺序或平台默认字符集，
  同一份文档两次解析就会得到不同的切片集合；对检索系统而言，
  这等于「同一份知识被静默改写」，而且无法复现问题。
- **确定性是可测试的强性质**：把「相同输入 + 相同配置 → 逐字节相同的输出」写成断言，
  比断言「切片看起来合理」强得多。
- **配置显式化**：`chunk-size`（默认 1000）、`overlap`（默认 150）、`max-chunks`（默认 5000）、
  `max-extracted-code-points`（默认 1,000,000）都写在 `application.yml` 里，
  因为**改动它们就是改动行为**，不应该藏在代码里的魔法数字。

### 为什么解析与切片不放在数据库事务里

- **解析是慢操作**（大 PDF 可能几秒到几十秒），而且与数据库毫无关系。
  持有事务只会长时间占用连接，把一个 CPU/IO 密集的任务变成连接池压力。
- **顺序固定**：读文档 → 比对版本 → 领取（CAS）→ **事务外**解析与切片 → 完成（原子写入）。
  事务只包住真正的原子单元。
- **代价是「领取」与「完成」之间有一个窗口**：此时数据库里的状态是 `PARSING`，
  而进程正在解析。窗口内的崩溃会留下悬挂状态，见下文「已知边界」。

### 为什么「完成解析」必须是一个原子端口方法

- 完成阶段要做四件事：校验行仍是 `PARSING` 且版本匹配 → 删除旧切片 → 插入新切片 →
  更新为 `PARSED` 并加版本。任何一步单独成功、其余失败都会留下自相矛盾的状态：
  「文档已 `PARSED` 但切片只有一半」「切片是新的但文档还在 `PARSING`」。
- **把这四步定义成端口上的一个方法，事务边界就属于适配器**：应用层继续保持
  「不认识事务」的纯粹性，而原子性由端口契约强制；JDBC 实现里它是一个 `TransactionTemplate`
  包住的整体，任一步抛异常就整体回滚。
- 切片数上限（默认 5000）保证这个事务不会无限增长；批量插入用循环 + 事务，
  而不是单条多值 `INSERT`（后者语句长度随切片数线性增长，容易撞上参数上限）。

### 为什么用 CAS 而不是「先查后改」

- 「先 SELECT 判断状态可领取，再 UPDATE」存在经典竞态：两个请求都可能看到 `UPLOADED`，
  于是**两个请求同时解析同一文档**，后写的那个把前者的切片整体替换掉 ——
  结果是「一次解析的产物被另一次覆盖」，而且两次都可能返回成功。
- CAS 的做法是行锁 + 带版本条件的更新：`SELECT version, status ... FOR UPDATE`
  再 `UPDATE ... WHERE id = ? AND version = ?`，并要求影响行数严格等于 1。
  并发下只有一个请求能成功，另一个拿到 412。
- 版本号同时是**对外契约**：它在 `ETag` 里，`If-Match` 携带它，
  因此「客户端拿到的版本」与「服务端认为的当前版本」始终是同一个概念。

### 失败语义与补偿

| 失败点 | 数据库里留下什么 | 处理 |
| --- | --- | --- |
| 命令非法 / 文档不存在 / 版本过期 | 什么都没变 | 400 / 404 / 412，**不发生任何写入** |
| 领取 CAS 失败（并发） | 什么都没变 | 412 |
| 状态不允许解析（`PARSING`/`PARSED`） | 什么都没变 | 409 |
| 读原文失败 / 解析失败 / 切片超限 | 文档 `PARSE_FAILED` + 稳定失败码 | 422 或 413；**没有切片** |
| 完成阶段写库失败 | 切片与状态整体回滚，然后文档被 CAS 成 `PARSE_FAILED` | 500；文档可重试 |
| 补偿写库也失败 | 文档可能停在 `PARSING` | 原始异常照常抛出，补偿失败只作为 suppressed |
| 进程在 `PARSING` 期间被杀 | 文档停在 `PARSING`（**悬挂**） | **本任务不实现恢复扫描**，如实记录为已知边界 |

- 失败码是**稳定枚举**（`KnowledgeParseFailureCode`），解析器异常只作为 cause 留在服务端，
  绝不进入数据库或响应；响应里额外返回 `failureCode` 供调用方分支。
- 「完成阶段失败」这一格需要特别说明：此时聚合对象可能已经被 `markParsed` 推进到 `PARSED`，
  而数据库写入整体回滚了。直接对同一对象调用 `markParseFailed` 会被领域层正确拒绝，
  因此补偿会先用当前字段**重建一个仍处于 `PARSING` 的等价聚合**再记录失败 ——
  否则文档会永远停在 `PARSING` 这个谁也领不走的状态。

## 解析安全边界

| 边界 | 做法 |
| --- | --- |
| 路径逃逸 | 只接受内容键；字符集白名单 + 解析结果必须仍在存储根目录内；**只读普通文件且不跟随符号链接** |
| 伪造格式 | 解析前校验文件头；不符即 `UNSUPPORTED_DOCUMENT_CONTENT` |
| 损坏文档 | 按异常**类型**映射为 `CORRUPTED_DOCUMENT`，不解析异常消息文本 |
| 加密文档 | `EncryptedDocumentException` / PDFBox `InvalidPasswordException` / POI `EncryptedDocumentException` → `ENCRYPTED_DOCUMENT` |
| 外部实体（XXE） | 解析只用本地解析器，Tika/POI 默认不解析外部实体；测试用「引用本地文件的 DOCX」验证内容绝不进入提取文本 |
| 资源耗尽 | 提取文本按 **code point** 限量，超限**立即中断**（自定义 SAX `ContentHandler`，不先构造完整字符串）；切片数量另有上限 |
| 非法 UTF-8 | 文本格式用显式 `CodingErrorAction.REPORT` 的严格解码器；默认的替换行为会把损坏内容静默变成 `U+FFFD` |
| 信息泄漏 | 响应里没有原文、切片内容、内容键、路径、解析器名称或异常文本；失败 `detail` 一律固定文案 |

## 已知边界（如实记录）

1. **`PARSING` 悬挂**：进程在解析期间崩溃（被杀、断电）会让文档停在 `PARSING`。
   它既不会自动重试，也不能被再次领取（状态机刻意不允许 `PARSING` 被二次领取）。
   本任务**不实现**恢复扫描任务；恢复方式是人工把状态改回 `UPLOADED`/`PARSE_FAILED`
   （README 与测试里给出了具体做法），或由后续任务实现超时回收。
2. **同步解析的时间上限**：请求会一直等到解析完成。极大文档可能触及客户端或反向代理超时；
   本任务不引入异步任务与消息队列，因此这是一个**已知的、刻意接受的**限制。
3. **`MAX_CHUNK_SIZE_LIMIT = 2000`** 由切片内容列容量反推（`VARCHAR(4000)`：
   UTF-16 长度最多是 code point 数的 2 倍），因此「把 chunk-size 调到 5000」会被启动期校验拒绝。
4. **读取路径的 TOCTOU**：`isRegularFile(NOFOLLOW_LINKS)` 与随后的 `newInputStream`
   之间存在一个极小的窗口。存储根目录是服务私有目录，且内容键由服务端生成，
   因此这个窗口在部署边界之内，已在此记录。
5. **符号链接测试在 Windows 上可能被跳过**：创建符号链接需要特权，
   无法构造该场景时测试会显式 skip（而不是假装通过）。

## 影响

正面：解析链路端到端可验证（真 PDF/DOCX/Markdown/TXT 都被真实解析过）；
切片确定性可断言；并发领取只有一个赢家；「切片 + 状态」整体原子；
失败可重试且不产生半个切片；解析库与切片算法都可以整体替换而不触及用例。

代价：多了一个第三方解析依赖族（Tika + POI + PDFBox）；同步解析占用请求线程；
`PARSING` 悬挂需要人工介入；解析文本的规范化与切片参数一旦调整，
历史切片与新切片会不一致（**这是「重新解析」而不是「迁移」**，本任务不做重新切片的批量任务）。

## 重新评估条件

1. 需要解析 PDF/DOCX 之外更多格式（如 XLSX/PPTX/HTML）时，把 `DocumentFormat` 与
   解析器选择扩成一张显式映射表（仍然不做自动探测）；
2. 出现「解析耗时超过请求超时」的真实需求时，再引入异步任务 + 状态轮询/回调，
   届时 `PARSING` 悬挂问题会由同一套机制解决；
3. 需要跨文档去重或增量重新解析时，评估内容寻址与切片版本化；
4. 切片参数需要按文档类型区分时，把当前单组配置升级为「按格式的配置矩阵」，
   并同步升级确定性断言的维度。
