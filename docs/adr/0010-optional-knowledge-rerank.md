# ADR 0010：可选的知识检索重排（RAG 6/6）

- 状态：已接受
- 日期：2026-09-16
- 决策范围：知识检索与问答之前的**可选二次排序**（DashScope qwen3-rerank）、
  `rerankScore` 与排序模式的审计契约、开关与失败语义

## 背景

RAG 第 4 步之后，检索能给出按**余弦相似度**排序的引用，第 5 步能基于这些引用作答。
但向量相似度只是「语义上像」，它并不直接回答「哪一段最能回答这个问题」：

- 余弦相似度对**主题相近但没回答问题**的切片同样友好（例如问「如何预防感冒」，
  「感冒是一种常见疾病」也会拿到不低的分数）；
- 相似度是**双编码器**（问题与切片各自编码）的结果，问题与切片之间没有交互，
  细粒度的相关性只能靠「把它们放在一起看」的模型才能分辨。

第 6 步要回答的是：**在不改变召回与阈值公开契约的前提下，允许对本次候选做一次可审计的二次排序**。

具体问题：

1. 重排放在哪一层？谁负责「一次重排、两处使用」？
2. 重排的输入输出契约是什么？供应商返回的顺序能不能信？
3. 重排分与向量分怎么共存才不产生歧义？
4. 关闭时怎样保证既有行为**逐字段**不变？
5. 上游失败、响应违约分别对应什么 HTTP 语义？能不能「失败就用向量排序」？
6. Endpoint 里的业务空间 ID 怎么处理？Key 从哪来？
7. 这一阶段**不**做什么？

本任务**不做**：扩大初召回池（例如「检索 100 条再重排取 5 条」）、改变 topK / minScore 语义、
混合检索或全文检索、把重排接入 Agent/MCP、流式输出、会话记忆、数据库迁移。

## 决策

1. **重排是 application 层的出站端口** `KnowledgeRerankPort`，只接受
   「规范化后的问题 + 按向量顺序排列的候选正文」，返回「原始下标 + 重排分」；
   HTTP 协议细节全部留在 infrastructure 的 `DashScopeKnowledgeRerankAdapter` 里；
2. **重排只在一处发生**：`KnowledgeRetrievalService`（检索用例）在向量结果校验之后、
   引用编号之前插入可选重排。检索接口与问答接口都通过这个用例取证，
   因此两者**必然**使用同一份最终排序 —— 这不是约定，而是结构上只有一条路径；
3. **只重排本次 topK 候选**，不扩大初召回池：因此本阶段的重排**不可能**找回向量检索未召回的切片；
4. **候选不足时不调用**：命中 0 条或 1 条时直接保留向量顺序，并在响应里如实报告
   `rankingMode = VECTOR_SIMILARITY`（报告事实，而不是开关状态）；
5. **按 `index` 绑定，不按到达顺序**：上游返回的每一条都必须携带候选在本次输入里的原始下标；
   下标缺失、负数、越界、重复，或条数与候选数不一致，一律整次失败（不猜测、不补齐）；
6. **分数必须是 `0..1` 的有限数值**：`NaN`、`±Infinity`、越界都是失败；
7. **按重排分降序，同分保持原向量排名**（稳定排序），保证同样的输入得到同样的顺序；
8. **两个分数分别保留**：`score` 仍然是向量余弦相似度，重排分放在新增的 `rerankScore`；
   排序模式放在 `rankingMode`，模型标识放在 `rerankModel`（未使用重排时不输出后两者）；
9. **默认关闭**：关闭时不要求 Endpoint、不要求 Key、不发起请求，响应里没有重排字段，
   既有行为逐字段不变；
10. **失败不降级**：上游不可用 → 502 `RERANK_PROVIDER_ERROR`；响应违约或端口违约 → 500。
    没有「失败就用向量排序」的分支。

## 理由

### 为什么重排在用例层，而不是在适配器或 HTTP 层

- **一处实现，两处受益**：把重排放进用例，检索接口与问答接口自动共享；
  放进任一 HTTP 入口，另一个入口就必须再写一遍，两者迟早会漂移；
- **它就是「证据顺序」的一部分**：引用编号、`allowedCitationIds`、`usedCitationIds`、
  提示词里的证据顺序都来自这一次排序，放在用例层才能保证它们来自**同一个顺序**；
- **适配器只翻译协议**：把 HTTP 细节（路径、字段、错误码）留在 infrastructure，
  应用层只认识「下标 + 分数」，换供应商不需要动用例。

### 为什么按 `index` 绑定，而不是按返回顺序

- 重排服务返回的是**按分数降序**的列表，它和输入列表的顺序**必然不同**（否则重排没有意义）；
  如果按到达顺序绑定，得到的会是「第 1 条分数给了第 1 个候选」这种看似正确、实则错位的映射；
- 上游文档明确 `index` 表示「该结果对应输入 documents 列表中的原始索引位置」，因此绑定是确定的；
- 绑定错了不会报错，只会让「引用 → 内容」错位，那正是最需要避免的静默错误。
  因此这里不仅按 `index` 绑定，还要求**完整覆盖且不重复**：少一条说明有候选没有分数，
  多一条说明来源不明，重复说明某个候选被打两次分而另一个没有。

### 为什么两个分数必须分开

- **语义不同**：向量分是「问题与切片各自编码后的相似度」，重排分是「把问题与切片放在一起看出来的相关性」；
  用一个字段轮流表达两者，会让「0.87」这个数字的含义随开关漂移，调用方无法解释；
- **可审计**：只有两个分数都在，调用方才能复核「重排把哪一条提到了前面」，以及「它原本的向量分是多少」；
- **`rerankScore` 不是绝对质量分**：它是**当前请求内**的相对分，用于对本次候选排序；
  不同问题、不同候选集合之间的分数不可比（上游文档亦有同样说明）。
  本文档不使用「相关性绝对提升」这类无法证明的表述。

### 为什么失败不降级

- **静默降级是假象**：上游挂了却返回向量排序，调用方看到 `200` 与一份合法引用，
  完全无法察觉「这次没有重排」；
- **开关与模式已经能表达「没重排」**：关闭或候选不足时，响应里的 `rankingMode` 就是
  `VECTOR_SIMILARITY` —— 那是一种**明确报告**的状态，而不是偷偷改变行为；
- **两类失败分开报告**：上游不可用（502，可重试）与响应违约（500，服务端/契约问题）
  是不同性质的问题，合并成一个码会让排障失去方向（同 ADR 0008 的检索端口收口原则）。

### 为什么 0/1 条候选不调用

- **顺序不可能改变**：一条候选无论怎么打分都排在第一位；
- **付费调用要有意义**：本阶段按调用计费，一条候选也要发一次请求属于纯浪费；
- **但必须如实报告**：因此 `rankingMode` 反映的是「这份顺序由什么决定」，
  而不是「开关是否打开」。语义边界写进了枚举的 Javadoc 与 README。

### Endpoint 与凭证

- DashScope 的文本重排地址形如 `https://{WorkspaceId}.<region>.maas.aliyuncs.com/...`，
  `{WorkspaceId}` 是**每个账号自己的业务空间 ID**。把它写进代码或默认配置，
  要么写死别人的空间、要么在仓库里留下账号标识。因此
  `flowdesk.knowledge.rerank.endpoint` **没有默认值**：开启重排必须显式配置，
  启动期校验拒绝空值、非法 URL、带用户信息/查询串/片段的地址，以及仍含 `{}` 占位符的地址；
- **Endpoint 必须是 HTTPS**（FD-0013-R1）：API Key 通过 `Authorization: Bearer` 请求头发送，
  明文 HTTP 会让它在链路上直接暴露。明文 HTTP **只允许本机回环字面量** ——
  那是自动化测试用本地合成端点验证真实报文的唯一途径，流量不出本机：
  - `localhost`（大小写不敏感）；
  - **完整的四段十进制 IPv4 字面量**且首段为 127（`127.0.0.0/8`）：恰好四段、每段 1~3 位十进制
    数字且取值 `0..255`、不接受前导零（`0127` 有八进制歧义）；
  - IPv6 回环 `::1` 及其完整写法 `0:0:0:0:0:0:0:1`（展开后八组，仅最后一组为 1）。
  - **不接受**「以 `127.` 开头」这种前缀判断（FD-0013-R2）：`127.example.com`、
    `127.0.0.1.attacker.example`、`127.5`、`127.999.999.999`、`0127.0.0.1`、`2130706433`、
    `::ffff:127.0.0.1` 一律按远程处理。前缀判断等于把「前缀是回环、实际由攻击者控制」的域名
    放进白名单，Bearer Key 就会被明文发往远端 —— 那正是 R2 修掉的问题；
- 回环判定只做**字面匹配**，不做 DNS 解析（校验阶段不得联网，
  而且「名字解析到 127.0.0.1」不等于「这就是本机端点」；白名单是「写法」而不是「解析结果」，
  因此不会随环境变化）；
- 这条边界由 {@code RerankEndpointPolicy} 实现，**配置校验与适配器构造器都调用它**。
  只在 Spring 装配层拦一次是不够的：适配器可以被直接 `new` 出来（测试、其它装配方式、
  将来的脚本），那时配置校验根本不会执行。失败信息只说明规则（必须 HTTPS、明文仅限回环），
  **不**回显 Endpoint、Key、主机名或任何请求内容；
- Key 沿用向量化的凭证原则（模态级 `spring.ai.dashscope.rerank.api-key` 优先，
  通用 `spring.ai.dashscope.api-key` 兜底，不读 `AI_DASHSCOPE_API_KEY`），
  只在 `Authorization: Bearer` 里发送，不进日志、不进仓库；
- 连接与读取都有**有界超时**，且本阶段**不做内部重试**：一次检索只调用一次重排。

### 下标必须能无损表达（FD-0013-R1）

上游返回的 `index` 必须是**整数类型**且**能无损装进 Java `int`**：

- `0.9`、`1.8`、`1e0` 这类小数与指数形式：拒绝；
- `4294967296`（2³²）、`-4294967296`、`2147483648`：超出 `int` 范围，拒绝；
- 字符串、布尔值、数组/对象：拒绝；
- 字段缺失或为 `null`：适配器表示为 `null`，由应用层的重排结果契约拒绝（缺失不是「默认 0」）。

为什么不能用 `intValue()` 了事：它会把 `0.9` 截断成 `0`、把 2³² 溢出成 `0`，
于是「这条分数属于第 0 个候选」变成一个**看起来合法、实际错位**的绑定 ——
排序对了、引用也「有据可查」，但指向的是另一段文本。这类错误不会报错，只会静默地错。
因此这里宁可整次失败：非法下标 → 500，不返回任何引用，也不继续调用 DeepSeek。

### 模型名为什么必须逐字匹配

请求体形状与响应形状都随模型/协议变化：`qwen3-rerank` 用扁平协议（`model`/`query`/`documents` 同级、
响应 `results` 在顶层），`gte-rerank-v2` / `qwen3-vl-rerank` 用 `input`/`parameters` 嵌套协议
（响应在 `output.results`）。本版本只实现前者，因此：

- 接受别的模型名，只会把「扁平请求」发给期望「嵌套请求」的接口，得到无法解释的响应；
- 模型名会被写进检索结果用于审计，写错就是一个错误的血缘声明；
- 因此它必须逐字等于 `qwen3-rerank`（不 trim、不改大小写），且只接受顶层 `results` ——
  **不**去兼容 `output.results`（那属于另一种协议，猜测只会掩盖配置错误）。

## 失败语义

| 失败点 | 模型是否被调用 | 对外 |
| --- | --- | --- |
| 重排上游超时、连接失败、被中断 | 否（检索阶段就失败） | 502 `RERANK_PROVIDER_ERROR` |
| 重排上游返回 429 / 5xx / 401 / 403 | 否 | 502 `RERANK_PROVIDER_ERROR` |
| 重排响应无法解释（非 JSON、缺顶层 `results`、元素/字段类型不对） | 否 | 500 `INTERNAL_SERVER_ERROR` |
| `index` 是小数/指数形式/字符串/布尔值，或超出 `int` 范围（FD-0013-R1） | 否 | 500 `INTERNAL_SERVER_ERROR` |
| `index` 缺失/负数/越界/重复/条数不全，或分数非 `0..1` 有限值 | 否 | 500 `INTERNAL_SERVER_ERROR` |
| 端口违反错误分类契约，或其它运行期异常 | 否 | 500 `INTERNAL_SERVER_ERROR`（收敛后） |
| 命中 0 条或 1 条 | 否（不调用重排） | 200，`rankingMode = VECTOR_SIMILARITY` |
| 正常 | 是（重排一次 + 生成一次） | 200，`rankingMode = RERANK` |

错误响应只含固定安全文案：不含 query、候选正文、上游响应体、Endpoint、Key、SQL 或异常类名。

## 已知边界（如实记录）

1. **只重排已召回候选**：不扩大初召回池，因此不可能找回向量检索未召回的切片；
2. **`rerankScore` 是请求内相对分**：跨请求不可比，不能当作质量基线；
3. **阈值仍在向量侧**：`minScore` 在重排**之前**过滤，重排不会把低于阈值的切片拉回来；
4. **不截断**：候选已经是 topK 条，重排只换顺序；
5. **不重试**：上游失败即终态；
6. **没有重排缓存**：同样的问题重复检索会再次调用重排（缓存属于另一个阶段的设计）；
7. **真实上游未验证**：`DASHSCOPE_LIVE=NOT_RUN`、`RERANK_LIVE=NOT_RUN`（本机无 Key、无 PostgreSQL、无 Docker），
   适配器测试使用本机合成 HTTP 端点，**不**访问真实付费接口。

## 影响

正面：检索结果从「语义上像」迈向「更能回答问题」；两个入口共享同一份最终排序；
顺序变化可复核（向量分与重排分都在响应里）；关闭时既有行为逐字段不变；
配置错误在启动期暴露（Endpoint/Key/模型名/与向量化的一致性）；失败不会被伪装成成功。

代价：开启后每次检索多一次上游调用，延迟与费用上升（候选 ≤ 1 条时不调用）；
排序质量取决于上游模型与候选集合；Endpoint 必须由部署方提供（没有默认值，
换来的是仓库里不出现任何业务空间 ID）。

## 重新评估条件

1. 召回质量成为瓶颈时：再评估**扩大初召回池 + 重排再截断**（那会改变 topK/minScore 的公开语义，
   需要单独一轮设计，不能顺手改）；
2. 需要跨请求比较重排分时：引入归一化或校准方案（当前分数只在请求内可比）；
3. 需要降低成本时：引入重排缓存或批量复用（注意缓存键必须包含候选集合与模型）；
4. 上游支持更多重排模型时：为「嵌套协议」另建适配器，而不是让同一个适配器猜两种形状；
5. 需要把重排结果反馈给上游做继续追问时：先定义「重排分是否属于可长期保存的审计字段」。
