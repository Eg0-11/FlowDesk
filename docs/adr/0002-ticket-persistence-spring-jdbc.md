# ADR 0002：工单持久化使用 Spring JDBC 与显式 SQL

- 状态：已接受
- 日期：2026-09-13
- 决策范围：FlowDesk 工单存储适配器的技术选型与并发实现方式

## 背景

工单应用层（`com.flowdesk.application.ticket`）已经把存储抽象为输出端口
`TicketRepository`，并把乐观并发写进了契约：

- 新工单版本为 0，每次成功更新严格加 1；
- `insert` 必须原子拒绝重复标识；
- `update` 必须是原子 compare-and-set，且「记录不存在」与「版本不匹配」必须区分。

现在需要给出真实实现。约束条件：

1. 目标数据库是 PostgreSQL；
2. 领域模型是不变式密集的聚合（状态与可选字段严格共存、完整时间链），
   数据库要作为最后一道防线保存同样的规则；
3. 需要能在没有外部依赖的情况下本地启动与跑集成测试。

## 决策

**使用 Spring JDBC 的 `JdbcClient` + 手写 SQL，配合 Flyway 迁移；不使用 JPA/Hibernate，也不使用 MyBatis。**

## 理由

### 为什么不用 JPA

- **乐观锁的表达力不足。** JPA 的 `@Version` 只能表达「读取时版本与当前版本一致」，
  但本项目的 `update` 契约要求：先判定记录是否存在（`TICKET_NOT_FOUND`），
  再判定版本是否匹配（`TICKET_VERSION_CONFLICT`），两者必须区分，且失败时不得产生部分写入。
  用 JPA 需要额外的查询或异常翻译才能区分，反而更绕。
- **领域模型与持久化模型的耦合。** 工单聚合刻意保持「纯 Java、无框架注解」，
  用 JPA 就必须引入实体注解或写一套映射层，前者污染领域，后者等于自己实现 ORM 的映射。
- **SQL 可控性。** 表上有 6 组 CHECK 约束（枚举取值、状态与字段组合、完整时间链、非空文本等）。
  这些是数据库契约，用 JPA 反而难以保证「迁移脚本与实体定义一致」。
- **依赖体积与启动成本。** Hibernate 引入的传递依赖与启动开销对本项目的收益为零。

### 为什么不用 MyBatis

MyBatis 同样能写显式 SQL，但需要引入 XML/注解映射与 SqlSession 生命周期管理；
而 `JdbcClient` 已经是 Spring 提供的一等公民，配合 `RowMapper` 完成同样的工作，
且不需要额外依赖与额外配置。

### 显式 SQL 如何落实 CAS

`JdbcTicketRepository.update` 在**同一个事务**内按顺序执行三步：

```sql
-- 1. 锁定目标行（不存在则查不到）
SELECT version FROM tickets WHERE id = ? FOR UPDATE;

-- 2. 版本比对在 Java 侧完成，不匹配直接抛 TICKET_VERSION_CONFLICT（不产生任何写入）

-- 3. 条件更新：id 与 version 同时匹配才写入，并把版本加 1
UPDATE tickets SET ..., version = version + 1
WHERE id = ? AND version = ?;
```

- **行锁**保证「读取当前版本」与「写入」之间不会有其它事务插进来改动同一行；
- **条件更新**是第二道保险：即使行锁被绕过，`WHERE version = ?` 也会让过期写入影响 0 行；
- 条件更新影响行数**必须严格等于 1**，否则按冲突处理并回滚；
- 整个流程由一个 `TransactionOperations` 包住，异常即回滚，因此 CAS 失败不会留下部分写入。

> **写事务的隔离级别刻意保持默认（`READ_COMMITTED`）。** CAS 的正确性来自行锁与条件更新，
> 与隔离级别无关，提升隔离级别只会增加锁竞争与序列化失败。列表查询另用一个
> **`REQUIRES_NEW` + 只读 + `REPEATABLE_READ`** 的事务模板（那是为了 COUNT 与分页查询看到同一快照，
> 且必须在已有事务中调用时仍然独立），两个模板互不影响，
> 见 [ADR 0004](0004-ticket-search-pagination.md)。

`insert` 则依赖**主键唯一约束**作为并发插入的最终防线：两个并发插入同一标识时只有一个成功，
另一个由数据库抛出重复键异常，适配器把它映射为 `TICKET_ALREADY_EXISTS`。
适配器**只**映射主键重复（`DuplicateKeyException`），其它完整性约束异常原样抛出，
不会被误判成「重复工单」。

### 为什么数据库也要保存领域约束

领域层是唯一权威，数据库是**最后一道防线**。把同样的规则写进 CHECK 约束的收益：

- 任何绕过聚合的写入路径（迁移脚本、运维手工 SQL、其它服务、未来的批量导入）
  都无法写进非法状态；
- 数据损坏会在写入时立刻暴露，而不是等到某次读取时才引发难查的领域异常；
- 这些约束同时是文档：`tickets` 表结构本身就说明了工单有哪些合法状态组合。

因此迁移脚本刻意重复表达了枚举取值、状态与可选字段的共存关系、完整时间链
（`created_at <= resolved_at <= closed_at <= updated_at`）、非空文本与字符串长度。

已知边界：SQL 标准的 `TRIM()` 只去除空格，不去除制表符等其它空白字符；
数据库因此拒绝空字符串与纯空格，而领域层的 `String.strip()` 还会拒绝其它 Unicode 空白。
两层的严格程度是「领域更严、数据库兜底」，不是完全等价。

### H2 与 PostgreSQL 的职责边界

| 环境 | 数据库 | 用途 |
| --- | --- | --- |
| 默认 profile | 内存 H2（`MODE=PostgreSQL`） | 本地开发、自动化集成测试；**不是生产数据库** |
| `postgres` profile | 真实 PostgreSQL | 生产与预发 |

H2 以 PostgreSQL 兼容模式运行，使同一份 Flyway 脚本与同一套 SQL 在两边都能执行；
所有约束都用标准 CHECK 表达，不使用任何数据库专属枚举类型或专属语法。
H2 承担 `H2_INTEGRATION` 的角色（真实 JDBC、真实迁移、真实并发线程），
但它**不能替代** PostgreSQL 验收：`POSTGRES_LIVE=NOT_RUN` 不等于 PostgreSQL 已验证。

## 影响

正面：SQL 完全可控、并发语义可审计、领域模型无框架污染、依赖轻、启动快。

代价：需要手写行映射；表结构变更要同时维护迁移脚本与映射代码；
没有 ORM 的脏检查与级联能力（本项目也不需要）。

## 重新评估条件

满足以下任一条件时重新评估：

1. 需要跨多张表的复杂对象图加载与级联写，且手写 SQL 的维护成本明显高于引入 ORM；
2. 需要支持多种异构数据库，且 SQL 方言差异成为主要成本；
3. 团队约定统一使用 ORM，且乐观锁的语义差异已通过统一基类解决；
4. 出现大量重复的手写映射代码，且无法通过少量映射器收敛。
