# ADR 0012：独立监控 MCP 服务与只读监控快照工具

- 状态：已接受
- 日期：2026-09-20
- 决策范围：`flowdesk-mcp-monitoring` 的 MCP 协议接入（Streamable HTTP）、
  `monitoring_snapshot_get` 只读工具的输入/输出契约、演示数据与真实数据的边界，
  以及它复用资产 MCP 服务已验收安全基线的代价与理由

## 背景

`flowdesk-mcp-monitoring` 此前只是一个「有健康检查的 Web 骨架」：能启动、能被探活，
但**不能被任何 MCP 客户端连接**，也没有任何工具。本任务把它建成真正可用的独立 MCP 服务，
并且只做一件事：**按资产标识查询一条只读监控快照**。

它不接入主 Agent，也不接入真实监控系统。它的价值在于为后续「Agent 联合调用资产与监控」准备好
第二个只读工具 —— 而这一步刻意做得与资产 MCP 服务**同构**：同样的协议、同样的安全边界、
同样的错误语义、同样的诚实边界（默认没有数据源）。

具体问题：

1. 工具输入怎么约束，才能让公布的 schema 与运行时校验完全一致？
2. 「没有这个资产的快照」与「监控数据源不可用」怎么区分？
3. 没有真实监控系统时，默认返回什么？演示数据怎么用才不会被误当成真实数据？
4. 资产 MCP 服务已经验收过的传输层保护（回环绑定、Origin 403、固定脱敏且有界的协议错误、
   会话与协议版本校验）要不要复制一份？
5. 本任务**不**做什么？

本任务**不做**：接入主 Agent 或 DeepSeek（工具不会注册到 ChatClient）、接入真实监控系统、
写操作（上报/修改监控数据）、鉴权/授权、数据库/Redis/MQ/前端/外部监控 SDK。

## 决策

1. **协议与端口与资产 MCP 服务同构**：Spring AI 1.1.2 的
   `spring-ai-starter-mcp-server-webmvc`（版本由既有 BOM 管理，不单独写版本），
   **Streamable HTTP**、端点 **`/mcp`**、端口 **8092**、服务器类型 `SYNC`；
2. **只注册一个只读工具 `monitoring_snapshot_get`**：唯一入参 `assetId`，
   格式固定 `AST-[0-9]{6}`；工具只读，没有上报/修改能力（连端口都没有写方法）；
3. **协议适配与查询逻辑分离**：`MonitoringSnapshotSource` 端口负责「查一条快照」，
   `MonitoringSnapshotGetTool`（Spring AI `ToolCallback`）负责输入校验、错误码与载荷形状；
4. **默认没有数据源**：`flowdesk.monitoring.source.mode=unavailable`（默认）时，
   每次查询都以稳定的 `MONITORING_SOURCE_UNAVAILABLE` 失败；只有显式设为 `demo` 才使用内置
   虚构数据，且所有结果都带 `source=DEMO`；
5. **模式值严格字面匹配**：只接受 `unavailable` 与 `demo`，未知值、大小写变体
   （`DEMO`/`Demo`）与带空白的值**一律启动失败**；
6. **快照不变量在构造期强制**：`health` 只能是四个枚举值之一，两个百分比必须在 `0..100`，
   告警数 `>= 0`，`observedAt` 必须是一个真实时刻；
7. **复用资产模块已验收的传输层保护**：回环字面量绑定、Origin 403、入口闸门（固定、脱敏、
   有界的协议错误 + 会话与协议版本校验）、`McpError` 安全序列化 —— 在监控模块内**各自实现一份
   等价的小型组件**，不引入跨模块依赖（见下文「代码重复的取舍」）。

## 理由

### 工具边界：一个只读查询，外加严格的输入形状

- **能力面越小越好**：这是一个独立进程，暴露给本机 MCP 客户端。只读查询已经能满足
  「看这个资产现在怎么样」，写能力（上报/修改）需要采集链路、鉴权与审计，本阶段明确不做；
- **「注册几个工具」必须可数**：工具通过 Spring AI `ToolCallback` Bean 注册，
  本模块**只有一个**这样的 Bean；回归测试同时断言「容器里恰好一个 ToolCallback」与
  「MCP 服务器自己的工具表里恰好一个 `monitoring_snapshot_get`」；
- **输入形状与 schema 一致**：只接受「**恰好**一个 `assetId` 字符串字段的 JSON 对象」。
  额外字段、字段名写错、`arguments` 不是对象、`assetId` 不是字符串、空串、超长、
  两段 JSON 拼接一律拒绝。schema 里写死 `required`、`additionalProperties=false`、
  锚定的 `pattern` 与 `maxLength`（值直接取自 `AssetId` 常量），**拒绝只改 schema 不改执行**；
- 不做 `trim`、不做大小写归一：`" AST-900001"`、`ast-900001` 都是非法输入，
  而不是「被修好再用」——输入规范化会掩盖调用方的错误。

### 数据来源：默认不可用，演示必须显式开启

- `Optional.empty()` 的含义是「**查过了，这个资产没有快照**」。在没有数据源的情况下给出这个答案，
  等于把「我们没有数据」说成「这个资产没有快照」；
- 因此默认装配的是「每次查询都明确失败」的实现，返回稳定的 `MONITORING_SOURCE_UNAVAILABLE`；
- 演示数据必须**显式**打开（`mode: demo`），而且数据是**固定**的：
  `AST-900001`（DEGRADED / 92 / 68 / 1）、`AST-900002`（HEALTHY / 18 / 35 / 0），
  `AST-900003` 刻意**没有**快照（用于验证「合法但未找到」）；
- `observedAt` 是**固定时刻**（`2026-01-01T00:00:00Z` 与 `2026-01-01T00:05:00Z`），
  工具不读取系统当前时间 —— 同样输入永远得到逐字节相同的输出，测试与演示都可复现；
- 演示数据用 `AST-9xxxxx` 保留段，一眼可辨；所有结果都带 `source=DEMO`。

### 「未找到」为什么不是错误

MCP 的 `isError` 表达的是「这次**调用**有没有失败」，不是「查询结果好不好」：

| 情形 | `isError` | 内容 |
| --- | --- | --- |
| 命中 | `false` | `{"assetId":"AST-900001","observedAt":"2026-01-01T00:00:00Z","health":"DEGRADED","cpuUtilizationPercent":92,"memoryUtilizationPercent":68,"activeAlertCount":1,"source":"DEMO"}` |
| 合法但没有快照 | `false` | `{"assetId":"AST-900003","found":false,"error":"MONITORING_SNAPSHOT_NOT_FOUND","message":"未找到该资产的监控快照","source":"DEMO"}` |
| 输入非法 | `true` | `{"error":"INVALID_ASSET_ID","message":"assetId 必须形如 AST-000001（AST- 加 6 位数字）"}` |
| 数据源不可用 / 内部异常 | `true` | `{"error":"MONITORING_SOURCE_UNAVAILABLE","message":"监控数据源当前不可用"}` |

- 「这个资产没有快照」是查询正常给出的答案（与检索接口「无命中返回 200 空列表」同一条原则）。
  标成错误会让调用方以为工具坏了，从而去重试或降级；
- **真正的执行失败**（输入非法、数据源不可用或内部异常）才置 `isError=true`；
- 「未找到」也带 `source`：**演示数据说没有**和**真实监控系统说没有**是两件事 ——
  为此端口上有一个只读的 `origin()` 方法，数据源不可用时则**不产生**任何来源声明；
- 错误内容里的文案是固定字符串，来自 `MonitoringToolError` 枚举：不含路径、配置、凭据、
  异常消息或上游原文。内部异常一律收敛为 `MONITORING_SOURCE_UNAVAILABLE`，
  日志里也只出现异常**类名**（不出现 assetId、监控数值、异常消息与堆栈）。

### 输出字段顺序与「不包含什么」

命中结果按固定顺序输出 `assetId`、`observedAt`、`health`、`cpuUtilizationPercent`、
`memoryUtilizationPercent`、`activeAlertCount`、`source`。
`MonitoringSnapshot` 这个类型上**根本没有** IP、主机名、内部地址、凭证或异常信息的字段，
因此它们不可能被工具「顺手」带出去 —— 这比「记得过滤」更可靠。

### 协议与安全策略：与资产 MCP 服务同一基线

监控服务要达到 FD-0014-R4 已验收的同等基线，逐条对应：

| 边界 | 做法 |
| --- | --- |
| 监听范围 | `server.address` 必须是**完整回环字面量**（`127.0.0.0/8` 四段写法或 `::1`），否则在**创建 Web 服务器之前**拒绝启动；`0.0.0.0`、外网地址、`localhost` 等主机名与含糊写法一律拒绝，判定只做字面匹配、不做 DNS |
| 浏览器跨源 | `/mcp` 只要带 `Origin` 头就返回固定 `403`（`ORIGIN_NOT_ALLOWED`），不配置宽松 CORS，Actuator 不受影响 |
| 能力声明 | 只声明 `tools`，显式关闭 `resources`/`prompts`/`completions`（Spring AI 的默认值都是 true）。**`logging` 关不掉**：MCP Java SDK 0.17.0 的 `McpAsyncServer` 构造器无条件加上它，无开关 —— 因此真实能力集是 `tools` + `logging`，按实测记录 |
| 会话 | 允许 `DELETE /mcp` 结束会话（`disallow-delete: false`）。拒绝它会让会话与其响应流一直存活，关停时 Tomcat 优雅关停等满 30 秒，测试 JVM 被 Surefire 强杀 |
| 协议错误 | 畸形报文、不是 JSON-RPC 请求、未实现方法、非法 `tools/call` 参数分别得到固定的 `-32700`/`-32600`/`-32601`/`-32602`，**普通 JSON（流立即结束）**、脱敏、可断言；请求体超过 1 MiB 得到 413 |
| 会话校验 | 非 `initialize` 的请求必须带**活跃**会话：缺失 → 传输层 400，伪造/空白/已删除 → 传输层 404。闸门不猜：读不到 SDK 会话表就全部放行 |
| 协议版本 | 校验在「会话之后、请求/通知分流之前」，因此**请求与通知同规则**：不受支持（含空白值）→ 400，通知的错误体是 `id:null` + 固定文案；缺失版本头继续兼容 |
| 无悬挂流 | 未实现的方法由闸门用普通 JSON 回答，不再落进 SDK 那条永不结束的响应流 |

### 代码重复的取舍（为什么暂不抽取公共 MCP 支持模块）

监控模块复用了资产模块**已验收**的四类传输层组件（逻辑等价、各自实现）：

| 组件 | 作用 |
| --- | --- |
| `McpRequestGateFilter` | 入口闸门：固定协议错误 + 会话与协议版本校验 |
| `McpTransportState` | 只读查询 SDK 会话表与传输层公布的协议版本 |
| `McpProtocolError` | 固定的错误码与文案 |
| `McpErrorJsonSerializer` | 兜底：`McpError` 不再按 `Throwable` 序列化 |
| `LoopbackAddressPolicy` / `MonitoringMcpBindingGuard` / `McpOriginRejectionFilter` | 回环绑定与跨源拒绝 |

**为什么先复制**：

1. **任务边界明确禁止跨模块依赖**：`flowdesk-mcp-monitoring` 只允许依赖 `flowdesk-shared`，
   而 `flowdesk-mcp-asset` 不是可依赖对象 —— 抽取公共模块意味着**新增一个模块**并改动
   一个已经验收的模块的依赖关系，超出本任务范围；
2. **资产模块已被验收，不应为了复用而改动**：它的这些组件带着 FD-0014-R1~R4 的验收结论，
   任何「顺手重构」都会让那份结论失效（需要重跑并重新取证）；
3. **两处的差异化空间还很大**：闸门的实现清单、工具层的错误码、数据源语义都不同，
   现在抽象容易抽出「又大又不合适」的接口；
4. **代价是可控的**：重复的是约 600 行**无状态、无业务耦合**的防护代码，彼此独立，
   且各自有测试（两套测试都在跑同样的边界）。

**将来抽取公共 MCP 支持模块的触发条件**（满足任意一条就应当抽取，而不是继续复制）：

1. 出现**第三个** MCP 服务（再多一份复制就不再是「取舍」而是「复制粘贴」）；
2. 这些组件需要**同步修改**（例如 MCP SDK 升级后闸门规则要变）—— 那时两处不一致的风险
   高于抽取成本；
3. 其中任一组件开始携带**业务语义**（例如闸门要认识具体的工具清单）——
   那说明它已经不该是通用组件，而是需要先拆分职责再抽取。

抽取时的目标形态：新建 `flowdesk-mcp-support`（只依赖 `flowdesk-shared` 与 MCP starter），
把上面五类组件搬进去，两个 MCP 服务改为依赖它，并把两套等价测试合并为一套参数化测试。

## 影响

正面：`flowdesk-mcp-monitoring` 从骨架变成可被真实 MCP 客户端连接、列出工具并调用工具的服务；
工具面最小（一个只读工具）；协议与查询逻辑分离；「没有数据源」与「没有快照」被明确区分；
输入形状、错误内容与输出字段顺序都是可断言的固定契约；安全基线与资产 MCP 服务一致；
不依赖资产模块或主服务的任何一层。

代价：演示数据是虚构的，真实监控系统尚未接入（`MONITORING_SOURCE_UNAVAILABLE` 是默认结果）；
没有鉴权与授权（因此严格限制在本机回环、且拒绝浏览器上下文）；工具只有单条查询，
没有列表、分页或历史区间；协议保护代码在仓库里有两份。

## 已知边界（如实记录）

1. **没有真实监控数据源**：演示数据是虚构的，测试也只验证了演示路径；
2. **没有鉴权**：任何能访问回环端口的本机进程都可以调用工具；
3. **只读、单工具**：没有上报/修改，也没有列表、分页、历史区间或聚合查询；
4. **只有 tools 能力**（外加 SDK 强加的 `logging` 声明）：不提供 resources / prompts / completions；
5. **不接入主 Agent**：工具不会注册到 DeepSeek ChatClient，也没有任何跨模块注册；
6. **协议保护代码有两份**（见上文取舍与抽取触发条件）；
7. **未验证项**：`MCP_LIVE=NOT_RUN`（未对接任何真实监控系统），
   `POSTGRES_LIVE`、`DASHSCOPE_LIVE`、`LIVE_SMOKE` 与本模块无关但全仓仍为 `NOT_RUN`。

## 重新评估条件

1. 接入真实监控系统时：新增 `MonitoringSnapshotSource` 实现并把 `mode` 扩展为 `real`
   （同时定义超时、重试与降级策略；届时 `source` 必须变成真实来源标识）；
2. 需要非本机访问时：**先**设计鉴权与授权，再放开回环限制 —— 顺序不能反过来；
3. 需要浏览器调用时：改成显式 CORS 白名单 + 鉴权，并重新评估 CSRF 面；
4. 需要写操作时：先补采集链路、审计、幂等与权限模型（不能只加一个工具）；
5. 出现第三个 MCP 服务或上述任一触发条件时：抽取 `flowdesk-mcp-support` 并合并测试。
